# 09. Ключевые сценарии

Пять сценариев составляют E2E-набор (Playwright) и демо на защите. Каждый — отдельный файл `apps/web/e2e/scenario-<буква>.spec.ts`.

## А. Покупка и оплата

1. Рыбак открывает водоём `CONNECTED`, выбирает тип разрешения и дату начала.
2. `POST /permits` → API проверяет BR-08, BR-09, создаёт `Permit(PENDING_PAYMENT)` и `Payment(PENDING)`, регистрирует транзакцию у провайдера, возвращает `paymentUrl`.
3. Рыбак платит на странице P24 (sandbox, тестовая карта) и возвращается на `/payment/return`.
4. P24 отправляет уведомление на `/payments/p24/notification`; API проверяет подпись, сумму, вызывает `transaction/verify`, ставит `Payment.SUCCEEDED` и `Permit.PAID`.
5. Страница возврата опрашивает `GET /me/permits/:id` (каждые 2 с, до 60 с) и показывает разрешение с QR.

Проверки: возврат браузера без уведомления не активирует разрешение; повторное уведомление ничего не меняет; неверная подпись → 400 и запись в лог.

## Б. Офлайн-запись и синхронизация улова

1. Рыбак с активным разрешением открывает `/catch/new` без сети.
2. Выбирает водоём (из разрешения, ближайший по GPS), вид, длину, вес, «оставлена/отпущена».
3. PWA вызывает `validateCatch` с кэшированными правилами и показывает нарушение сразу.
4. Улов сохраняется в `catchQueue` (`PENDING_SYNC`).
5. Сеть появилась → `POST /catches/sync`; сервер повторно валидирует уловы дня в порядке `caughtAt` в транзакции.
6. Статусы обновлены; `REJECTED` показан с причиной.

Проверки: два офлайн-устройства с уловами сверх лимита → второй отклоняется сервером; повторная отправка → тот же результат.

## В. Проверка инспектором

1. Рыбак показывает QR (работает офлайн — токен в IndexedDB).
2. Инспектор сканирует обычной камерой телефона → открывается `/verify/:token`.
3. Без входа видна публичная информация; инспектор организации-владельца видит имя, год рождения, тип, срок и уловы за сегодня.
4. Инспектор сохраняет протокол OK/VIOLATION с заметкой.

Проверки: подделанный токен → «недействительно»; аннулированное разрешение с валидной подписью → «недействительно»; инспектор другой организации видит только публичные данные.

## Г. Улов на неподключённом водоёме

1. Рыбак находит водоём `UNCLAIMED`; карточка показывает użytkownika rybackiego и ссылку на его сайт.
2. Купив разрешение вне платформы, добавляет `ExternalPermit` (выдавший, номер, срок, водоёмы, фото).
3. Записывает уловы как в сценарии Б; проверяются общие правила.
4. В конце сезона скачивает PDF-реестр и отправляет владельцу.

## Д. Подключение организации

1. Представитель регистрирует организацию; суперадмин активирует её.
2. Админ организации находит свои водоёмы в каталоге и подаёт claim с документом.
3. Суперадмин одобряет: водоём `CONNECTED`, принадлежит организации.
4. Админ создаёт тип разрешения, правило водоёма и приглашает инспектора; у водоёма появляется кнопка «Купить».

## Сквозной MVP (ворота 10-й недели)

Д (сокращённо, через seed) → А (fake-провайдер) → Б (онлайн) → В. Тест `scenario-mvp.spec.ts` должен проходить в CI до начала этапа «Расширение».
