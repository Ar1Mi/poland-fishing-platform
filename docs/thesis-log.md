## 2026-10-31 · T-18 Реестр уловов (онлайн)

**Сделано:**
- `CatchesModule`: `POST /catches/sync`. Пакет до 100 уловов проверяется `validateCatch` из `shared` в порядке `caughtAt` в одной транзакции; каждый улов сохраняется `ACCEPTED` или `REJECTED` с нарушениями. Повтор `clientId` возвращает сохранённый результат (ADR-0009). Ещё `GET /me/catches` за сезон, `PATCH` и `DELETE` в окне BR-07.
- Контекст валидатора собирается из чужих модулей только через их сервисы: разрешения — новый `CatchPermitsService` из `PermitsModule` (платформенные и внешние), правила — `SpeciesRulesService.effectiveOnWaters`, затем виды и водоёмы. Справочники читаются несколькими запросами на весь пакет, до транзакции.
- Web: `/catch/new` — один экран формы и экран вердикта сервера (NFR-06). `/me/catches` — реестр по дням с переведёнными причинами отказа (`RuleAlert`), правкой на месте и удалением с подтверждением. В `shared` добавлены окно BR-07 (`catchEditableUntil`), схема формы улова, вес в кг без float, перевод варшавского «дата + время» в момент и обратно.

**Решения (подтверждены пользователем):**
- Область дневного лимита (вопрос, отложенный из T-17) — все водоёмы пользователя с самым строгим пределом водоёма улова. Точный вариант (у каждого уровня своя область) потребовал бы менять контракт валидатора и офлайн-данные PWA. Упрощение строже точного, а не мягче, как и упрощения seed. Цена — рыба того же вида с водоёма другого владельца в тот же день засчитывается в лимит организации.
- `PATCH` применяет правку и снова проверяет улов: статус меняется в обе стороны. Так отклонённый улов можно исправить (например, добавить вес при `WEIGHT_REQUIRED`). Остальные уловы суток не пересматриваются: принятое не становится нарушением задним числом.
- `externalPermitId` поддержан в API сразу: формат запроса из `05-api.md` его уже содержал. Проверка — только по общим правилам. Для T-22 остаются CRUD, фото и UI.
- Свои решения в рамках документов. Одновременные синхронизации одного пользователя упорядочены `pg_advisory_xact_lock` по ключу пользователя, а не `FOR UPDATE` строки `User`: таблица чужого модуля, и блокировка мешала бы её внешним ключам. Неизвестная ссылка (разрешение, вид, водоём) отклоняет весь пакет с 400: это ошибка ввода, а не нарушение правила. Окно BR-07 — буквально «конец суток + 24 ч», поэтому в дни перевода часов оно кончается в 23:00 или 01:00, и интерфейс показывает точное время.

**Проблемы:**
- Три e2e-теста падали с 401 после сдвига часов: access-токен живёт 15 минут по тем же подменённым часам. Помогает `moveTo()`: часы сдвигаются, затем снова вход.
- `IsRFC3339` пропускал `2026-02-30T10:00:00Z`, а `new Date` молча переносит такую дату на 2 марта. Дата проверяется ещё и строгим ISO 8601; тест закрепляет это.
- Полный набор e2e нашёл старый тест покупки со сравнением всего объекта разрешения: в ответе появилось поле `waters`. Это намеренное расширение контракта, поэтому ожидание дополнено, а не ослаблено.
- В браузере щука 45 см была принята, хотя я ждал отказа. Ошибался я: в seed предел щуки 45 см, граница включительна. Отказ показал улов 44 см. Там же видно, что `GET /species` сортирует по сопоставлению БД («Łosoś» в конце): форма улова сортирует сама, для остальных экранов записано в «На потом».
- В web нет прямой зависимости `zod`, поэтому выбор водоёма сделан обычным состоянием React рядом со схемой формы из `shared`: в select всегда допустимое значение, проверка ему не нужна.
- Два одинаковых доступных имени найдены тестами: скрытый заголовок вердикта дублировал заголовок блока (теперь фокус получает сам заголовок блока), ссылка «Moje zezwolenia» совпала с иконкой шапки.

**Подтверждение:**
- `apps/api/test/catches.e2e-spec.ts` — 44 теста. Мутации: без блокировки тест «два телефона одновременно» падает в 3 из 3 запусков (4 угря при лимите 2). Если при `PATCH` считать сам улов, падает тест «не считает сам улов». Весь API: 447 e2e, 218 unit.
- `packages/shared/src/rules/catch/br-07-edit-window.test.ts` (полночь по Варшаве, сутки 23 и 25 ч), `catches/catch-input.test.ts`, `time/warsaw.test.ts` (несуществующий час 29.03, двойной час 25.10). Shared — 334 теста; покрытие `src/rules` — 100 % строк, 98,86 % ветвей.

- Браузер, 375 px, локальный API: форма на одном экране 375×812; 45 см принято; 44 см → «Poniżej wymiaru ochronnego», `BR-02 · BELOW_MIN_LENGTH`; поправка на «Wypuszczona» → «Przyjęty» (секунды `caughtAt` в БД не изменились); удаление с подтверждением.

**Для текста:**
- `apps/api/src/modules/catches/catches.service.ts:76-117` — сердце синхронизации. Сортировка по `caughtAt`, общий список `kept`, в который попадает каждый принятый улов пакета, и одна и та же чистая функция `validateCatch`, что будет и в PWA.

## 2026-10-31 · T-17 CatchValidator

**Сделано:**
- `validateCatch` в `packages/shared` (FR-12, ADR-0008): чистая функция без БД и часов, одна и та же для PWA офлайн (T-21) и сервера (T-18). Каждое правило BR-01…BR-06, BR-10, BR-11 — объект `CatchRule` (Strategy) в своём файле со своими тестами; `DEFAULT_CATCH_RULES` задаёт набор и порядок.
- Контракт уточнён в `02-business-rules.md` до кода: типы `CatchInput` / `PermitSnapshot` (платформенное или внешнее разрешение), состав `details` каждого нарушения, включительные границы.
- Покрытие `src/rules` измеряется (`@vitest/coverage-v8`) с порогом 90 %; шаг в CI.

**Решения (подтверждены пользователем):**
- Возвращаются **все** нарушения, а не первое: рыбак сразу видит, что улов, например, и мал, и в запретный период. BR-01 разделено на две проверки с одним ID — «неактивно» и «чужой водоём» срабатывают вместе.
- BR-01 проверяется на момент `caughtAt`, а не `now`: улов, записанный офлайн и отправленный после конца срока, принимается. Статус берётся из `effectivePermitStatus` (ADR-0005); внешнее разрешение передаётся туда как `PAID` — для него работают только даты. `REVOKED` неактивно для любого улова, даже пойманного до аннулирования (`revokedAt` не учитывается).
- Сутки лимитов — варшавский календарный день: валидатор сам отбирает из `sameDayKept` оставленные уловы того же вида за те же сутки. Какие водоёмы туда входят, решает вызывающий код — вопрос отложен в T-18 (см. «Проблемы»).
- В лимит идут и **более поздние** уловы тех же суток: лимит ограничивает итог дня, а принятый улов не пересматривается. Если два телефона вместе превысили лимит, отклоняется улов, синхронизированный позже (сценарий Б). Альтернатива «только уловы раньше по `caughtAt`» делала результат независимым от порядка синхронизации, но либо пропускала превышение итога, либо требовала переводить принятый улов в `REJECTED` задним числом.
- Вес не указан при весовом лимите: BR-11 требует вес, а BR-05 срабатывает, если лимит уже достигнут без этой рыбы — любая рыба что-то весит, поэтому при лимите 0 (no-kill) нарушение есть всегда. Ранний улов без веса (принят до появления лимита) считается как 0 г.

**Проблемы:**
- Формулировка лимита в документе «по всем водоёмам, где действует то же правило» не определяет область лимита организации и водоёма: точный вариант — лимит каждого уровня со своей областью (общий — все водоёмы, организации — её водоёмы), но `EffectiveRule` хранит после слияния одно число. Валидатор от этого не зависит (считает то, что ему передали); решение записано в ROADMAP как вопрос T-18.
- Все тесты прошли с первого запуска — поэтому проведена ручная мутационная проверка: 11 внесённых ошибок (`<` ↔ `<=` на каждой границе, сутки по UTC вместо Варшавы, учёт отпущенной рыбы, BR-01 по `now` вместо `caughtAt`) ловятся. Первая мутация BR-01 была бесполезной — неопределённая переменная роняла все 20 тестов с `ReferenceError`; заменена настоящей (`now` вместо `caughtAt`), её ловят 6 тестов.
- Ревью перед PR (`code-reviewer`): (1) в документе было «уловы за сутки **до этого улова**», а я молча заменил это на «кроме проверяемого», и тест закрепил новый смысл. Вынесено на решение пользователя, выбран вариант «все уловы суток», он записан в документ (см. «Решения»). (2) Фильтр суток проверялся только с одной стороны — улова из следующих суток не было ни в одном тесте, и неверный фильтр «с начала варшавских суток» (`>= day`) проходил все 72 теста. Добавлены уловы следующего дня в тесты BR-04/BR-05, полуночи и обоих переходов времени; мутант `>= day` теперь ловят 5 тестов. Мелкое: пример `details` в `05-api.md`, «вида» в строке BR-05, `RangeError` на неверных датах контекста описан в документе.
- Текстовый отчёт покрытия Vitest 5 скрывал полностью покрытые файлы: таблица показывала только `species-rules.ts`, и казалось, что папка `catch` не измеряется. Проверено через `json-summary` (все файлы 100 %), в конфиге включён `skipFull: false` — таблица стала доказательством критерия.

**Подтверждение:**

**Для текста:**

## 2026-10-30 · T-16 Правила: CRUD и слияние уровней

**Сделано:**
- `resolveEffectiveRule` в `packages/shared` (ADR-0008): самое строгое значение каждого параметра трёх уровней — наибольший `minLengthCm`, наименьшие дневные лимиты (`null` — нет лимита, 0 — no-kill), все запретные периоды без склейки. Одна и та же функция будет работать в PWA офлайн и на сервере (T-17, T-21).
- API: `/admin/rules` (общие, суперадмин), `/orgs/:orgId/rules` (организация и её подключённые водоёмы, ORG_ADMIN), публичный `GET /waters/:id/rules` — эффективные правила по видам. Все изменения пишутся в AuditLog в транзакции действия.
- Web: страница «Zasady połowu» в панели организации (список, форма, удаление со вторым кликом) и раздел «Zasady połowu» на карточке водоёма с пометкой охраняемых видов.

**Решения:**
- Правило мягче верхнего уровня **сохраняется**, а не отклоняется (решение пользователя): слияние всё равно его не применит, а общее правило может позже измениться. Чтобы админ это видел, ответ API несёт `ineffective` — параметры, перекрытые более строгим уровнем; считает их `ineffectiveParameters` в `shared` через то же слияние. Альтернатива — открыть общие правила для ORG_ADMIN и сравнивать на клиенте — дублировала бы логику уровней.
- Применимые уровни водоёма — общие + правила **текущей** организации водоёма (без водоёма и этого водоёма). Правило бывшего владельца не действует, даже если осталось в БД; правила организации действуют и при `BLOCKED` (водоём остаётся `CONNECTED`, регламин не отменён).
- `PATCH` меняет только параметры: пропущенный — без изменений, `null` снимает ограничение; вид и уровень зафиксированы (`forbidNonWhitelisted` даёт 400). Правило проверяется **после** слияния с сохранённым — иначе снятие последнего параметра или одного конца периода прошло бы проверку DTO.
- Проверки по полям — `class-validator` в DTO, проверки над параметрами вместе («что-то ограничивает», «оба конца периода») — общая Zod-схема `ruleParametersSchema`, та же, что в форме web. `02-29` не принимается: период «до конца февраля» хранится как `02-28` и в високосный год покрывает 29-е (`isInClosedPeriod`).
- Второе общее правило вида — новый код 409 `RULE_ALREADY_EXISTS`; гонку двух созданий решает уже существующий частичный индекс `rule_one_general` (P2002 → тот же код).

**Проблемы:**
- Правило `shared` «сначала документ, потом тесты, потом код» нарушено на первом шаге: функция слияния написана до раздела в `02-business-rules.md`. Документ дописан до тестов и коммита.
- Пометку «не действует» в первой версии нельзя было показать: ORG_ADMIN не видит `/admin/rules`. Решено полем `ineffective` в ответе (см. выше), документ и тесты дописаны перед UI.
- В браузере на 375 px бейдж «Gatunek chroniony — tylko wypuścić» выходил за край карточки (`whitespace-nowrap` бейджа); разрешён перенос строки. Проверка в браузере показала и верное поведение на равных значениях: общее правило щуки — 45 см, правило организации 45 см не помечено, 40 см — помечено.
- Ревью перед PR (`code-reviewer`): два одновременных `PATCH` одного правила проверялись каждый против старой строки — вместе могли оставить половину периода (500 на CHECK) или правило без ограничений. Исправлено `SELECT … FOR UPDATE` перед чтением; тест держит строку в открытой транзакции, ждёт, пока запрос встанет на блокировку, и коммитит — без блокировки он падает (мутационная проверка). Первая версия теста (два `PATCH` через `Promise.all`) проходила и без блокировки: гонка не воспроизводилась, тест был бесполезен. Добавлен тест двух одновременных созданий общего правила (201 + 409), строка «no-kill» не дублируется при двух нулевых лимитах, ошибка «правило ничего не ограничивает» объявляется скринридеру (`role="alert"`).
- Осознанно не исправлено: форма отправляет все параметры, поэтому две правки одного правила из двух браузеров — «последний записавший побеждает» (API сам по себе меняет только присланные поля). Для одного админа кружка допустимо.
- Существующие тесты карточки водоёма падали на неожиданных запросах (`/waters/:id/rules`, `/species`) — моки дополнены, проверки не менялись. Тест соответствия кодов ошибок документу дополнен новым кодом.

**Подтверждение:**
- `packages/shared/src/rules/species-rules.test.ts` — 7 комбинаций уровней, порядок, `null`/0, периоды, `MM-DD`, Zod-схемы API и формы, `ineffectiveParameters`.
- `apps/api/test/rules.e2e-spec.ts` (42) — CRUD обоих уровней, 403 чужому админу на каждом маршруте `/orgs/:orgId/rules`, 404 правила другого уровня, валидация, 409, AuditLog, слияние для подключённого/неподключённого/заблокированного/сменившего владельца водоёма, правка под чужой блокировкой, одновременные создания; `species-rules.service.spec.ts`.
- `apps/web/src/features/rules/pages/rules-pages.test.tsx`, `lib/format-rule.test.ts`.
- `pnpm lint`, `pnpm typecheck`, `pnpm test` (shared 237, api 218, web 212), `pnpm --filter api test:e2e` (403) — зелёные. Ручная проверка на 375 px: создание и изменение правила, пометка «Nie obowiązuje», карточка Zalewu Zegrzyńskiego.

**Для текста:** `packages/shared/src/rules/species-rules.ts` → `resolveEffectiveRule`, `ineffectiveParameters` — слияние уровней и пометка недействующих параметров через одно и то же слияние (правила как данные, ADR-0008); `apps/api/src/modules/rules/species-rules.service.ts` → `effectiveForWater` — выбор применимых уровней водоёма (текущий владелец, а не любой, кто когда-то задал правило); там же `lockForChange` — почему проверка «правило целиком» требует блокировки строки.

- API: `GET /me/permits` (все разрешения, новые сверху), `qrToken` в `GET /me/permits/:id` и в ответе покупки, `GET /me/permits/:id/pdf` — A4 с данными владельца, водоёмами и векторным QR.
- Web: «Moje zezwolenia» (актуальные / архив), страница разрешения (`PermitTicket` из дизайн-системы, QR на весь экран, скачивание PDF), QR на странице возврата после оплаты.

**Решения:**
- `exp` = следующая местная полночь (`warsawDayEnd` в `shared`), а не `validTo 23:59:59 UTC`: иначе летом QR действовал бы до 01:59 следующего дня по Варшаве. Смещение берётся через `Intl` в 00:00 UTC следующего дня: Польша меняет смещение в 01:00 UTC, поэтому в этот момент смещение то же, что в местную полночь. Отдельная библиотека часовых поясов не нужна.
- Без `iat`: подпись Ed25519 детерминирована, поэтому одно разрешение — один токен. Ответ стабилен, его можно кэшировать офлайн (T-21).
- `qrToken` во всех ответах о разрешении, включая список: подпись Ed25519 стоит микросекунды, зато объект везде одинаковый (документ «permit — тот же объект, что GET /me/permits/:id» остаётся верным).
- Ключи — обязательные переменные окружения; проверка при старте через `node:crypto` (тип Ed25519 и совпадение публичного с приватным). Иначе ошибка проявилась бы только при первом QR. В тестах и при экспорте OpenAPI пара генерируется на лету, ключей в репозитории нет.
- PDF: pdfkit + qrcode (решение пользователя). Встроенные шрифты PDF (WinAnsi) не содержат ą, ł, ś, поэтому статические TTF Onest (OFL, шрифт дизайн-системы) лежат в `apps/api/assets/fonts`. Сборки `@fontsource` для web не подошли: в них woff2 разбиты на latin/latin-ext, а pdfkit не умеет подставлять глифы из второго шрифта. QR в PDF рисуется квадратами (вектор), а не PNG — чёткий при печати.
- PDF только для `SCHEDULED`/`ACTIVE`, иначе новый код 422 `PERMIT_NOT_VALID`: QR в документе истёкшего разрешения вводил бы в заблуждение. Текст PDF — польский независимо от языка интерфейса (документ для польского водоёма и инспектора).
- `/offline-bundle` перенесён в T-21 (решение пользователя): эффективных правил ещё нет (T-16/T-17), а потребитель — PWA.
- Web: URL в QR строится из `location.origin`; сайт отдаётся с `WEB_URL`, поэтому совпадает с URL в PDF. Слой «QR на весь экран» — `div role="dialog"`, а не `<dialog>`: `showModal` в jsdom нет.

**Решения:**

Порядок полей контрольных сумм: register — `sessionId, merchantId, amount, currency, crc`; уведомление — `merchantId, posId, sessionId, amount, originAmount, currency, orderId, methodId, statement, crc`; verify — `sessionId, orderId, amount, currency, crc`. SHA-384, hex.
- P24 считает сумму от PHP `json_encode(..., JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES)`. `JSON.stringify` даёт ту же строку (кроме U+2028/U+2029, которые PHP экранирует, — в наших полях их нет), поэтому сериализатор не нужен. Тест закрепляет это на `statement` со `/` и польской буквой.
- Подпись уведомления сравнивается за постоянное время (`timingSafeEqual`).
- `timeLimit` транзакции = `PAYMENT_TIMEOUT_MINUTES` (30) сужает окно оплаты после нашего таймаута, но не закрывает его: P24 считает от регистрации, а мы — от записи `Payment`, чуть раньше. Опоздавшее уведомление застаёт платёж `FAILED`, verify не вызывается, P24 вернёт деньги плательщику.
- Неподлинное уведомление → 400 `VALIDATION_FAILED`, без нового кода ошибки: фронтенд этот маршрут не видит. Тело уведомления — формат провайдера, поэтому его проверяет адаптер (Zod), а не DTO с `class-validator`.
- Маршрут P24 отвечает 404 вне режима `p24` (`PaymentsService.processProviderNotification`), как фейковый — вне `fake`: фейковый адаптер подпись не проверяет, и иначе в dev-режиме был бы второй путь бесплатной оплаты. Нашло ревью.
- Фильтр по IP-адресам P24, рекомендованный документацией, не включён — принятый риск в `07-security.md`. За туннелем или прокси адрес источника недостоверен, а без CRC-ключа подделать уведомление нельзя, и verify всё равно идёт к P24.
- `Organization.p24MerchantId` не используется: один sandbox-аккаунт платформы (ADR-0004).

**Проблемы:**
- Документация P24 — SPA: `WebFetch` получает пустую страницу, поэтому текст читался через браузер.

**Решения** (первые три согласованы с автором до кода):
- У проданного типа условия зафиксированы: срок, льгота и водоёмы → 409 `PERMIT_TYPE_IN_USE`, удаление — только у непроданного, проданный снимают с продажи (`isActive`). Водоёмы типа определяют, что покрывает уже проданное разрешение (BR-01): изменение задним числом расширило бы или отняло права у купивших. Название и цена следующих покупок меняются (уплаченная сумма хранится в `Permit.pricePaidGrosze`). Новый код ошибки, а не `VALIDATION_FAILED`: запрос корректен, мешает состояние данных.
- Цена «od» — отдельный эндпоинт, а не поле `GET /waters`: `PermitsModule` зависит от `WatersModule`, обратная зависимость дала бы цикл модулей (`forwardRef`) и нарушила таблицу зависимостей `03-architecture.md`. Клиент делает один запрос на показанные карточки (до 100 id).
- Изменения типов, включая цену, пишутся в `AuditLog` — раньше журнал покрывал только claim, правила и блокировки (`07-security.md` дополнен).
- «od» — минимум по активным **обычным** типам: льготная цена для подростка вводила бы в заблуждение взрослого. Публичные списки показывают только то, что можно купить сейчас: тип активен, организация `ACTIVE`.
- PATCH сравнивает значения, а не наличие полей: форма может прислать проданный тип целиком, неизменённые условия не считаются попыткой их изменить; водоёмы сравниваются как множество. Запрос без изменений не пишет журнал.
- Водоёмы чужой организации или неподключённые → 400 `VALIDATION_FAILED` в `details.fields.waterIds`. Граница модулей уточнена в `03-architecture.md`: связь `PermitType` ↔ `FishingWater` ведёт `PermitsModule` (`connect`/`set`, фильтр по связи), а поля водоёмов — название, статус, владелец — читаются только через `WatersService` (`findNames`, `findConnectedIds`, `findOwners`).

**Проблемы:**
- Гонка «изменение типа ↔ продажа»: проверка «разрешений нет» и изменение водоёмов в одной транзакции не защищают от вставки `Permit` между ними. Обычный `UPDATE` берёт `FOR NO KEY UPDATE`, а FK-проверка вставки — `KEY SHARE`; они совместимы, продажа не ждёт. Решение — `SELECT … FOR UPDATE` строки типа перед подсчётом. Тест держит открытую транзакцию продажи и ждёт по `pg_stat_activity`, пока PATCH встанет на блокировку. Без `FOR UPDATE` (проверено) изменение водоёмов проходит мимо продажи, а удаление ждёт FK и падает 500.
- Инструмент записи файлов записал `\u00a0` в регулярном выражении как настоящий неразрывный пробел — ESLint (`no-irregular-whitespace`) остановил коммит. `\s` в JS уже покрывает U+00A0 и U+202F, выражение упрощено.
- В тестах web `mockApi` бросает ошибку на неожиданный запрос, но клиент превращает её в `UNKNOWN_ERROR` запроса, и тест проходит: после добавления «od» старые тесты каталога молча делали неописанный запрос. Обработчики добавлены; сам хелпер — кандидат на исправление отдельно.
- Ревью (`code-reviewer`) нашло 500 на `PATCH` с `null` в любом поле: `PartialType` навешивает `@IsOptional()`, который пропускает и `null`, а сравнение полей считало `null` изменением (на проданном типе — ложный 409). Update-DTO переписан явно с `IfPresent()` (`ValidateIf(v => v !== undefined)`, как в профиле); правила полей описаны один раз и общие для создания и правки. Там же: тест INSPECTOR был только для POST (теперь на каждом маршруте), «od» не проверяла, что водоём всё ещё у организации типа, повтор id в `lowest-prices` давал дубликаты, после 409 в интерфейсе оставался устаревший список (теперь перезагружается при любом исходе).

**Решения** (первые четыре согласованы с автором до кода):
- `AuditService.record(tx, …)` внутри транзакции решения, а не интерсептор из `03-architecture.md`: интерсептор пишет после ответа, вне транзакции, и не знает об автоматически отклонённых заявках. Изменение без записи в журнале (и наоборот) невозможно. Интерсептор для действий без своей транзакции остаётся в T-26; `03-architecture.md` обновлён.
- Новый код `CLAIM_NOT_PENDING` (409, `details.status`) для повторного решения: отдельный от `WATER_ALREADY_CONNECTED`, чтобы интерфейс объяснял, что именно произошло.
- Документ скачивает только суперадмин, всегда как вложение (`attachment` + `nosniff`): загруженный файл никогда не открывается как содержимое сервиса.
- Тип документа — по сигнатуре (`file-type`, та же версия, что уже тянет `@nestjs/common`, стала прямой зависимостью), белый список вместо `image/*` из документа (SVG — тоже image, но с исполнимым содержимым).
- Порядок блокировок при одобрении: сначала условный `UPDATE` водоёма (`WHERE status = 'UNCLAIMED'`), затем заявки. При обратном порядке два одновременных одобрения заявок одного водоёма блокировали бы строки заявок крест-накрест (deadlock → 500); так второе ждёт водоём и получает 409. Конкурирующие заявки отклоняются одним `updateManyAndReturn` — их id сразу идут в `diff` журнала.
- Подача заявки читает водоём `SELECT … FOR SHARE` в своей транзакции (найдено ревью, см. «Проблемы»): блокировка конфликтует с `UPDATE` одобрения, и новая заявка либо отклоняется этим одобрением, либо получает 409.
- Одобрение только для `ACTIVE`-организации (`ORG_NOT_ACTIVE`, 403), отклонение — для любой: одобрение безвозвратно закрывает заявки конкурентов, а заблокированная организация не продаёт. Решение принято по замечанию ревью; автор может его пересмотреть.
- На клиенте нет второй копии правил доступа: страница показывает переведённый отказ API (`ORG_SCOPE_VIOLATION`, `ORG_NOT_ACTIVE`). Размер и тип файла проверяются до отправки только ради быстрого ответа; решает сервер по содержимому.

**Проблемы:**
- `file-type` — только ESM, а API собирается в CommonJS: подключён через динамический `import()` (как в `FileTypeValidator` Nest); проверено и в Jest, и в собранном `dist`.

**Решения:**

## 2026-10-21 · T-07 Аутентификация

**Сделано:**
- API: регистрация с письмом подтверждения, verify-email, вход, refresh с ротацией и обнаружением повторного использования, выход, сброс пароля; глобальный `JwtAuthGuard` с `@Public()` и `@CurrentUser()`; `GET/PATCH /me`.
- Модули `AuthModule` (токены), `UsersModule` (таблица `User`), `NotificationsModule` (письма pl/en/ru через SMTP/Mailpit) — по правилу «чужие таблицы только через сервис».
- Web: страницы входа, регистрации, подтверждения email и сброса пароля (React Hook Form + Zod-схемы из `shared`), access-токен только в памяти, тихий refresh при старте и повтор запроса после 401, язык интерфейса из профиля.

**Решения:**
- Access JWT подписывается `jose` (HS256), а не `@nestjs/jwt` + passport: та же библиотека нужна для QR (ADR-0006), guard из 30 строк понятнее стратегий passport. `currentDate` берётся из `ClockService`, поэтому истечение токена тестируется без ожидания.
- Refresh — случайные 256 бит, в БД только SHA-256; «семья» на каждый вход. Предъявление отозванного токена отзывает всю семью (кража обнаруживается, страдают и вор, и владелец). Срок скользящий: каждая ротация — ещё 7 дней.
- Новый код `INVALID_TOKEN` (400) для неизвестной/использованной ссылки отдельно от `TOKEN_EXPIRED` (401): UI по-разному объясняет «ссылка уже использована» и «ссылка устарела, запросите новую». Решение согласовано с автором.
- Согласие RODO только проверяется (`acceptTerms: true`), поле в схеме не добавлялось — факт регистрации и есть запись. Пароль 8–128 символов без требований к составу (NIST SP 800-63B); ссылки 24 ч / 1 ч.
- Против перечисления email: одинаковый ответ forgot-password, письмо уходит без ожидания (время ответа не выдаёт адрес), вход с неизвестным email сверяет пароль с фиктивным argon2-хешем. `EMAIL_NOT_VERIFIED` — только после верного пароля.
- Три именованных лимита `@nestjs/throttler`: login 5/мин на IP + email (перебор одного аккаунта замедлен, пользователи за одним NAT не блокируют друг друга); общий потолок 20/мин на IP для публичных auth-маршрутов (каждый анонимный запрос может стоить argon2 на 64 МиБ или письма); forgot-password 3/ч на email. Reset-password проверяет токен до хеширования.
- Ротация и отзыв refresh-токенов одного пользователя сериализуются `pg_advisory_xact_lock(userId)`: без строки чужой таблицы `User` и без изменения схемы.
- Сброс пароля подтверждает email (ссылка доказывает владение ящиком) и отзывает все refresh-токены — это заодно выход из тупика «потерял письмо подтверждения».

**Проблемы:**
- `@InjectPinoLogger` в новых сервисах ломал DI: nestjs-pino создаёт провайдеры контекстов при объявлении `LoggingModule`, а файлы сервисов импортируются позже. Заменено на `PinoLogger` + `setContext()`.
- Свойство Swagger `default` у необязательного `locale` openapi-typescript превратил в обязательное поле клиента — `default` убран в описание.
- У `argon2` есть install-скрипт, запрещённый политикой `allowBuilds`; пакет поставляет готовые бинарники, поэтому скрипт явно отключён (`argon2: false`) с комментарием.
- Гонка двух вкладок: обе обновят токен одной cookie, и вторая будет принята за повторное использование → выход. Внутри вкладки refresh один на всех (общий промис); между вкладками — известное ограничение, кандидат на BroadcastChannel/Web Locks.
- Бандл web вырос 447 → 592 кБ (gzip 142 → 185) в основном из-за Zod; разделение кода по маршрутам или `zod/mini` — в T-29.
- За прокси (Caddy, T-30) `req.ip` станет адресом прокси — нужен `trust proxy`, иначе throttler будет считать всех одним IP.
- Ревью (субагент `code-reviewer`) нашло гонку: refresh вора в момент сброса пароля оставлял рабочий токен. Отзыв (`UPDATE … WHERE userId`) ждёт блокировку строки, которую держит ротация, и после её коммита перепроверяет только «свои» строки (READ COMMITTED) — вставленный ротацией преемник он не видит. Первое исправление (повторять `UPDATE`, пока что-то обновляется) было ложным: HTTP-тест с параллельными запросами проходил и с ним, и без него — окно гонки слишком узкое. Детерминированный тест, держащий транзакцию «ротации» открытой, показал, что повтор не помогает (первый проход обновляет 0 строк и цикл сразу заканчивается). Рабочее решение — advisory-lock; мутационная проверка (убрать lock → тест падает) подтверждает, что тест ловит ошибку.
- Тест конкурентного refresh сначала проверял только «не больше одного успеха» и проходил при любом исходе; переписан на настоящий инвариант: после двух одновременных refresh одной cookie в семье нет ни одного рабочего токена.
- Лимит по IP сначала не срабатывал: ключ счётчика throttler по умолчанию включает маршрут, поэтому «20 в минуту на IP» на деле было «20 на каждый маршрут». Для этого лимита задан свой `generateKey` без маршрута.
- Счётчики throttler идут по `Date.now()`, а не `ClockService`, поэтому сброс лимита через минуту/час не тестируется (ограничение библиотеки).

- Источник seed — rozporządzenie 2023 г. (оно отменило предыдущие акты). Где значения зависят от участка реки, взят самый строгий вариант: нижний уровень правил не может ослабить общий, поэтому мягкое значение нельзя было бы исправить. Не моделируются запреты по дням недели (łosoś, troć) и сокращение периода в праздник; certa не включена: самый строгий вариант закрыл бы её на 10 месяцев в году. Всё записано в `02-business-rules.md` → «Общие правила в seed».
- Клиент генерируется как CommonJS с импортами без расширения (`importFileExtension = ""`) и не коммитится — его создаёт `postinstall`. `prisma.config.ts` читает `.env` из корня сам: Prisma 7 этого больше не делает.

## 2026-10-13 · T-02 Пакет `shared`

**Сделано:**
- Все 15 enum модели данных, `ErrorCode` (HTTP-ошибки) с таблицей HTTP-статусов и `CatchErrorCode` (нарушения правил улова) — как `as const`-объекты с одноимённым типом-объединением.
- Утилиты времени: `warsawDate(date)` — календарный день в `Europe/Warsaw`, `isInClosedPeriod(date, from, to)` — okres ochronny в формате `MM-DD` с переходом через Новый год.
- `effectivePermitStatus(permit, now)` — вычисляемые статусы `SCHEDULED / ACTIVE / EXPIRED` для оплаченного разрешения (ADR-0005).
- Сборка `tsc` в ESM + `.d.ts` (`dist/`), Vitest, 33 unit-теста.

**Решения:**
- Enum — `as const`-объекты, а не `enum` TypeScript: такую же форму генерирует Prisma, значения взаимно присваиваются без приведения типов и на фронтенде остаются обычными строками.
- Варшавские сутки считаются через встроенный `Intl.DateTimeFormat` с `timeZone: 'Europe/Warsaw'`, без `date-fns-tz`: база часовых поясов есть и в Node, и в браузере, а `shared` остаётся без зависимостей (ADR-0003). `docs/03-architecture.md` → «Время» обновлён.
- Даты действия разрешения в `effectivePermitStatus` — строки `YYYY-MM-DD`, а не `Date`: это календарный день, а не момент времени. Сравнение `warsawDate(now)` с ними — сравнение строк, поэтому формат проверяется (`assertDateOnly`, `RangeError`): `@db.Date`, сериализованная как `2026-07-01T00:00:00.000Z`, иначе молча давала бы `SCHEDULED` в первый день действия. `validTo` включительно: разрешение активно до варшавской полуночи после последнего дня.
- Границы периода в `isInClosedPeriod` включительны; неверный формат `MM-DD` даёт `RangeError`, а не тихое «не попадает» — иначе опечатка в правиле отключала бы запрет.
- 29 февраля запретно всегда, когда запретно 28 февраля. Период «do końca lutego» хранится как `…02-28`; при простом сравнении строк `MM-DD` охрана вида в високосный год снималась бы на день. Правило записано в `docs/02-business-rules.md` → «Уточнения».
- Коды нарушений улова отделены от `ErrorCode`: они не становятся HTTP-ошибкой, а приходят в `violations` ответа синхронизации. Тест проверяет, что два набора не пересекаются.
- Приложения видят `@lowisko/shared` через `exports` → `dist`, то есть только после сборки. Поэтому `shared` собирается при `pnpm install` (`prepare`) и перед корневым `pnpm typecheck`, а его скрипт `dev` — `tsc --watch`. Альтернатива (экспорт исходников через custom condition) отвергнута: API на CommonJS и web на Vite пришлось бы настраивать по-разному.
- Версия Vitest вынесена в `catalog:` — она понадобится и в `apps/web` (T-05).

**Проблемы:**
- Тест «enum совпадают с Prisma» написать нельзя, пока нет схемы; критерий перенесён в T-04.
- Проверено опытом (временный импорт в `apps/api` и `apps/web`): с собранным `shared` typecheck проходит, без `dist` — TS2307. Отсюда сборка перед typecheck. Сами зависимости `workspace:*` приложения добавят в T-03 и T-05.
- Предупреждения из журнала T-01 подтвердились и учтены: `vitest.config.ts` включён в `tsconfig.json` (иначе ESLint не находит проект), а сборка идёт по отдельному `tsconfig.build.json` с явным `rootDir` и без тестов.
- Ревью (`code-reviewer`) нашло два места, где неверные данные давали бы тихо неверный результат: даты разрешения не в формате `YYYY-MM-DD` и 29 февраля вне периода `…02-28`. Оба исправлены и закрыты тестами. Ещё два замечания оформлены критериями: Jest в API должен загрузить ESM-only пакет (T-03), CI собирает `shared` до `lint` и `test` (T-06).

**Подтверждение:**

## 2026-10-06 · T-01 Монорепозиторий и инструменты

**Сделано:**

**Решения:**
- Node 24 — действующая LTS; Node 20 вышла из поддержки, а lint-staged 17 требует Node ≥ 22.22. Версию проверяет `devEngines.runtime` с `onFail: error`: поле `engines` само по себе pnpm не останавливает. Версия pnpm закреплена полем `packageManager` (corepack), версия TypeScript — через `catalog:` в `pnpm-workspace.yaml`, одна на все пакеты.
- TypeScript 6.0.3, а не 7.0: `typescript-eslint` 8.71 поддерживает только `<6.1.0`, а без него нет типового линтинга.
- В базовом tsconfig `lib: ["ES2023"]` и `types: []`: в `shared` нет ни DOM, ни Node-глобалов, поэтому требование ADR-0003 «чистый TypeScript» проверяет компилятор, а не ревью. `web` добавляет DOM у себя.
- Запрет строк в JSX собран из двух правил. `i18next/no-literal-string` в режиме `jsx-only` проверяет текст, шаблонные литералы и видимые атрибуты (`title`, `placeholder`, `alt`, `aria-label`, `aria-description`, `label`); технические (`className`, `type`) не трогает. Плагин пропускает любые атрибуты на `<a>`, `<svg>`, `<text>` и `label`/`aria-description` на нативных тегах — это закрывают два селектора `no-restricted-syntax`. Файлы `*.test.tsx` исключены.
- Граница проверки: строки вне JSX (`toast('...')`, переменная с текстом, `.ts`-файлы) линтер не видит, это остаётся на ревью.
- Markdown исключён из Prettier: он выравнивает таблицы пробелами, это около 400 изменённых строк в 22 файлах документации и шумный diff при каждой смене статуса в ROADMAP.
- Корневые `dev`, `build`, `test` запускаются с `--if-present`: тестовые раннеры появляются в T-02, T-03, T-05, а не здесь. Пока флаг стоит, пакет без скрипта `test` молча выпадает из прогона, поэтому снятие флага с `build` и `test` записано критерием в T-06.
