```markdown
**Решения:** что выбрали и почему (ссылка на ADR, если есть).
**Проблемы:** что не сработало сразу и как решили.
**Подтверждение:** тесты, метрики, скриншоты (пути к файлам).
**Для текста:** фрагмент кода или идея, которую стоит показать в дипломе (путь:строки).
```

## 2026-10-19 · T-05 Каркас web

**Сделано:**
- SPA на Vite 8 + React 19: React Router (data router), TanStack Query, Tailwind 4. Layout mobile-first со ссылкой «к содержимому», заглушка главной (проверяет связь с API через `/health`), страница 404 и запасная страница ошибки маршрута.
- Тема Tailwind из токенов `10-design-system.md` (цвета, шкала текста, радиусы, кольцо фокуса); шрифты Onest и IBM Plex Mono из бандла; компоненты `Button`, `Input`, `Badge`, `Alert`, `Card` в стиле shadcn/ui и `ApiErrorAlert`.
- react-i18next: `pl` полностью, `en`/`ru` — с откатом на `pl`, переключатель языка в шапке.
- Типизированный API-клиент: `pnpm gen:api` (OpenAPI → `openapi-typescript`) + `openapi-fetch`, единая обработка `{ code }` и перевод ошибок.

**Решения:**
- Документ OpenAPI выгружает отдельный скрипт API (`apps/api/src/openapi/export-openapi.ts`). Ему не нужны ни БД, ни `.env`: Prisma подключается лениво, окружение задано фиксированно. Так типы клиента не зависят от локальной настройки и собираются в CI без запущенного сервера. `schema.d.ts` не коммитится (решение T-01); его генерируют корневые `pnpm lint` и `pnpm typecheck`, около 5 с на `nest build`.
- В dev Vite проксирует `/api` на API. Браузер работает с тем же origin, что и в prod за Caddy, поэтому клиенту не нужен адрес API в конфигурации.
- У клиента два своих кода сверх `ErrorCode`: `NETWORK_ERROR` (нет ответа или прокси вернул 502/503/504 без тела API) и `UNKNOWN_ERROR` (тело не в формате `{ code }`). Компоненты видят только `ApiError.code`, а сообщение — `t('errors.' + code)`. Ответы 4xx не повторяются, сеть и 5xx — до двух раз.
- i18n: один файл на фичу (`locales/{lng}/{feature}.json`), при загрузке они сливаются в одно пространство под именем фичи. Ключи выглядят как `home.page.title`, как требует `06-frontend.md`, и проверяются компилятором по ресурсам `pl` (`i18next.d.ts`). Язык браузера не определяется: по умолчанию `pl`, выбор хранится в `localStorage`.
- Шрифты (ADR-0011): `@fontsource` не даёт отдельных CSS по наборам символов с `unicode-range` для Onest Variable, а у Plex Mono наборы без `unicode-range` перекрывали бы друг друга. Поэтому `@font-face` описаны вручную только для latin, latin-ext и cyrillic: шесть файлов woff2, около 115 КБ.
- Зависимости сверх перечисленных в `06-frontend.md` — стандартный набор shadcn/ui (`class-variance-authority`, `clsx`, `tailwind-merge`, `@radix-ui/react-slot`, `lucide-react` для иконок статусов). Тестовые: `jsdom`, Testing Library.

**Проблемы:**
- Свежие релизы `react-router`, `@tanstack/react-query` и `i18next` (вышли в день задачи) отклонила политика минимального возраста пакетов pnpm, и `pnpm add` сам дописал исключения в `pnpm-workspace.yaml`. Исключения убраны, версии закреплены на релизах на несколько дней старше.
- `openapi-fetch` запоминает `globalThis.fetch` при создании клиента, и подмена `fetch` в тестах на него не действовала. Клиенту передан `fetch`, который каждый раз берёт глобальную функцию заново.
- При остановленном API Vite-прокси отвечает 502, и пользователь видел «что-то пошло не так» вместо «нет связи». Ответы 502/503/504 без тела API теперь сводятся к `NETWORK_ERROR`.
- В скрипте выгрузки окружение нужно задать до загрузки `AppModule`: `ConfigModule` решает, читать ли `.env`, при импорте. Динамический `import()` в CommonJS-сборке требовал расширений путей, поэтому окружение вынесено в модуль `fixed-env.ts`, который импортируется первым.
- `openapi-typescript` 7 объявляет peer `typescript ^5`, а в проекте 6.0.3. Генерация работает, предупреждение pnpm остаётся.
- Фирменное кольцо фокуса (Toń 700) почти не видно на тёмной шапке; там у элементов белое кольцо.

**Подтверждение:**
- `pnpm --filter web test` — 50 тестов:
  - `apps/web/src/shared/api/{errors,client}.test.ts`: тело ошибки API, неизвестный код, не-JSON, 502/503/504, сбой сети, отмена запроса, тот же origin и префикс `/api/v1`;
  - `apps/web/src/shared/i18n/i18n.test.ts`: у каждого `ErrorCode` и клиентского кода есть польский текст, в `en`/`ru` нет ключей, которых нет в `pl`;
  - `apps/web/src/app/routes.test.tsx`: 404, статус API, переведённая ошибка с кодом, переключение языка с `lang` и `localStorage`, откат на `pl`;
  - `apps/web/src/app/query-client.test.ts`, `apps/web/src/shared/ui/button.test.tsx`.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm format:check`, `pnpm build` — код 0; `pnpm --filter api test:e2e` — 72 теста (вынесение `createOpenApiDocument` не изменило `/api/docs-json`).
- Вручную в браузере на 375 px: главная с API (Połączono) и без него (сообщение и код), 404 на `ru` после перезагрузки (язык запомнен), кольцо фокуса 3 px с отступом 2 px. Загружаются только нужные наборы шрифтов (`document.fonts`).

**Для текста:** `apps/web/src/shared/api/errors.ts:35-56` и `apps/web/src/shared/api/client.ts:20-35` — как стабильный `code` из `05-api.md` проходит от фильтра исключений API до переведённого сообщения в UI, включая отказы, которых сервер не формирует (сеть, прокси). `apps/web/src/shared/i18n/i18n.ts` + `i18next.d.ts` — требование «строки только через ключи» проверяет ещё и компилятор: несуществующий ключ — ошибка типов.

## 2026-10-19 · T-04 БД

**Сделано:**
- PostgreSQL 16 и Mailpit в `docker-compose.yml`; Prisma 7.10.0 с `prisma.config.ts` и драйвер-адаптером `@prisma/adapter-pg`; схема v1 (18 моделей, 15 enum) и первая миграция со всеми CHECK-ограничениями и частичным индексом из `04-data-model.md`.
- `PrismaService`, `PermitNumberService` (номера `ZW-{YYYY}-{000001}`), `DATABASE_URL` в Zod-схеме env.
- Seed: 20 видов (pl/en/ru) и 16 общих правил по Rozporządzeniu MRiRW z 12.07.2023 (Dz.U. 2023 poz. 1373); повторный запуск ничего не дублирует и возвращает исправленные вручную значения.
- Инфраструктура интеграционных тестов: один контейнер Testcontainers на прогон, отдельная БД на каждый тест-файл, фабрики `test/factories`.

**Решения:**
- Последовательность номеров — своя на каждый год, её создаёт SQL-функция `next_permit_number(year)` при первом номере года. Таблица-счётчик отвергнута: это новая сущность в модели, а пропуски номеров (откат транзакции) для разрешения не важны. Год считается по дате в `Europe/Warsaw`, а не в UTC.
- `CREATE SEQUENCE IF NOT EXISTS` при одновременных вызовах падает на уникальном индексе `pg_class`, поэтому создание идёт под `pg_advisory_xact_lock`. Блокировка берётся только пока последовательности нет — остальные покупки года не выстраиваются в очередь.
- Источник seed — rozporządzenie 2023 г. (оно отменило предыдущие акты). Где значения зависят от участка реки, взят самый строгий вариант: нижний уровень правил не может ослабить общий, поэтому мягкое значение нельзя было бы исправить. Не моделируются запреты по дням недели (łosoś, troć) и сокращение периода в праздник; certa не включена: самый строгий вариант закрыл бы её на 10 месяцев в году. Всё записано в `02-business-rules.md` → «Общие правила в seed».
- Клиент генерируется как CommonJS с импортами без расширения (`importFileExtension = ""`) и не коммитится — его создаёт `postinstall`. `prisma.config.ts` читает `.env` из корня сам: Prisma 7 этого больше не делает.
- Тестовые БД — копии шаблонной (`CREATE DATABASE … TEMPLATE`): миграции применяются один раз через `prisma migrate deploy`, копия создаётся за миллисекунды, файлы тестов идут параллельно без общей очистки таблиц.
- Скрипты установки разрешены только `@prisma/engines` (скачивает schema engine для `migrate`); `prisma`, `esbuild`, `ssh2`, `cpu-features`, `protobufjs` работают без них. `pg` и `@types/pg` напрямую не добавлены — их приносит адаптер.
- Демо-данные (`SEED_DEMO`) требуют пользователей и организаций — остаются критерием T-20.
- По итогам ревью схема отступила от умолчаний Prisma: правила организации и водоёма удаляются вместе со своим уровнем (`Cascade`), внешнее разрешение с уловами удалить нельзя (`Restrict`), общее правило — одно на вид (частичный уникальный индекс `rule_one_general`). Изменения внесены в init-миграцию: она ещё не попала в `main`.

**Проблемы:**
- Официальное руководство Prisma + NestJS на 2026-10 уже описывает ветку 8.x; конфиг 7.x сверялся по типам установленного `@prisma/config`. Там же выяснилось, что `env()` бросает исключение без переменной — `prisma generate` в CI без БД упал бы, поэтому `datasource` задаётся только при наличии `DATABASE_URL`.
- Сгенерированный клиент импортирует `./internal/class.js`; Jest не находил файл (в исходниках `.ts`), а `moduleNameMapper` не действует на `globalSetup`. Решено опцией генератора, а не настройкой Jest.
- Prisma 7.10.1 вышла за три дня до задачи и не проходит политику `minimumReleaseAge` — зафиксирована 7.10.0.
- Поиск по названию в API ISAP не находит действующее rozporządzenie; акт нашёлся через поиск в сети и проверен по ELI (`DU/2023/1373`, статус «obowiązujący»).
- `lpad` в PostgreSQL обрезает строку длиннее заданной: миллионный номер года стал бы `ZW-2026-000000`. Замечено при проверке функции, исправлено и покрыто тестом.
- Ревью (`code-reviewer`) нашло, что у необязательных связей `SpeciesRule` Prisma по умолчанию ставит `ON DELETE SET NULL`: при удалении организации её правила молча стали бы общими для всей страны. Исправлено (см. «Решения»), закрыто тестом. Оно же показало, что тест параллельной нумерации проверял только вызовы вне транзакции, а блокировка и новая последовательность в транзакции покупки держатся до её конца; добавлены тесты с открытой транзакцией (commit и rollback), ограничение записано в `04-data-model.md` для T-13. Мелкие правки: значения всех 16 правил сверяются тестом с таблицей, набранной отдельно от seed; воркеры Jest получают заведомо недоступный `DATABASE_URL`, чтобы тест без своей БД падал, а не писал в общую; контейнер останавливается при ошибке миграции.

**Подтверждение:**
- `apps/api/test/database-constraints.e2e-spec.ts` — каждое ограничение отклоняет неверную строку и пропускает верную (период через Новый год, бесплатный тип разрешения, PENDING-заявка после решения по прошлой); правила удаляются вместе с организацией и водоёмом; второе общее правило вида отклоняется. `prisma migrate diff` между применённой миграцией и схемой пуст.
- `apps/api/test/permit-number.e2e-spec.ts` — нумерация с 000001, смена года в 00:00 по Варшаве (23:00 UTC), 10 одновременных первых запросов года, ожидание за открытой транзакцией покупки (commit и rollback), отсутствие ожидания для последующих номеров, 7-значный номер.
- `apps/api/test/seed.e2e-spec.ts` — 20 видов и 16 правил, значения каждого правила, повторный запуск, охраняемый вид; `apps/api/src/database/enums.spec.ts` — 15 enum `shared` совпадают с Prisma.
- `pnpm lint`, `pnpm typecheck`, `pnpm test` (shared 33, api 55), `pnpm --filter api test:e2e` (72), `pnpm format:check`, `pnpm build` — код 0. Собранное приложение стартует и отвечает на `/api/v1/health`; без `DATABASE_URL` не стартует.

**Для текста:** `apps/api/prisma/migrations/20261018095038_init/migration.sql:524-549` — нумерация разрешений по годам в одной SQL-функции: последовательность на год, advisory lock только на создание, защита от обрезки `lpad`; `apps/api/prisma/reference-data.ts:109-149` — как правовой текст с вариантами по участкам рек сводится к одному правилу данных (самый строгий вариант) и почему.

## 2026-10-13 · T-03 Каркас API

**Сделано:**
- Приложение NestJS 12 в `apps/api`: конфиг с Zod-схемой env (без валидного окружения процесс не стартует), префикс `/api/v1`, Swagger на `/api/docs`, `GET /api/v1/health`.
- Единый формат ошибок `{ code, message, details? }`: `DomainError`, глобальный `HttpExceptionFilter`, `ValidationPipe` с `details.fields`.
- Логи pino с request-id (`X-Request-Id`), helmet, CORS только на `WEB_URL`, `ClockService` как единственное место чтения системных часов.
- Jest: 36 unit- и 17 интеграционных тестов; API зависит от `@lowisko/shared` через `workspace:*`.

**Решения:**
- NestJS 12 поставляется только как ESM, но приложение оставлено на CommonJS (так решено в T-02). Jest 30 загружает ESM-пакеты через `require(esm)`; условие — Node ≥ 24.9 и флаг `--experimental-vm-modules`. Флаг зашит в скрипты `test`/`test:e2e`, а `engines` ужесточён до `^24.9.0`. Трансформация `node_modules` в Jest не понадобилась, тесты исполняют тот же `dist`, что и приложение.
- `GET /health` размещён под общим префиксом (`/api/v1/health`): в продакшне Caddy проксирует только `/api`.
- В `ErrorCode` добавлен `INTERNAL_ERROR` (500): таблица кодов в `docs/05-api.md` была «минимальным набором» без кода для необработанного исключения. Причина 500 пишется только в лог, клиент получает фиксированный текст.
- Исключения фреймворка кода не несут — фильтр подбирает его по статусу (401/403/404/429, прочие 4xx → `VALIDATION_FAILED`). Объекту с полем `statusCode` фильтр доверяет, только если это ошибка body-parser (`expose` + `type`): иначе 401 от внешнего сервиса превратился бы в 401 для пользователя и разлогинил бы его.
- pino-http подключён первым Express-middleware, а nestjs-pino работает в режиме `useExisting`. Стандартное подключение nestjs-pino — это Nest-middleware: оно срабатывает после парсера тела и только под префиксом.
- `NODE_ENV` по умолчанию `production`: режим разработки (уровень debug, `pino-pretty` из devDependencies) включается явно через `.env`.
- `WEB_URL` и `API_URL` принимаются только как origin без пути — `WEB_URL` сравнивается с заголовком `Origin`.
- Install-скрипты зависимостей запрещены в `pnpm-workspace.yaml` (`allowBuilds`): `@scarf/scarf` — телеметрия, `@parcel/watcher` и `unrs-resolver` приходят готовыми бинарниками. Версия zod взята 4.6.5: 4.6.7 вышла менее суток назад, и pnpm отклоняет её политикой `minimumReleaseAge`.

**Проблемы:**
- Первый запуск Jest упал с «Must use import to load ES Module»: сообщение советует Node 24.9+, хотя стоял 24.21. Причина нашлась в исходниках `jest-runtime` — проверяется `vm.SourceTextModule`, доступный только с `--experimental-vm-modules`.
- `pnpm add` с точной свежей версией zod молча дописал исключение `minimumReleaseAgeExclude`, а после его удаления lockfile пришлось править вручную — `pnpm install` не перерешивал версию.
- Ревью (`code-reviewer`) показало на собранном приложении, что запросы, отклонённые до маршрутизации (битый JSON, 413, пути вне `/api/v1`), не логировались, шли без request-id, а неизвестный путь отвечал HTML-страницей Express. Исправлено порядком middleware и JSON-ответом 404; закрыто тестами.
- То же ревью: фильтр отдавал клиенту `message` у `HttpException` 5xx и доверял любому `statusCode` 4xx; redact заголовков не был покрыт тестами. Исправлено, тесты добавлены.
- `expect.any()` типизирован как `any` и не проходит типовой линтинг — в тестах значение сужается до `unknown`.

**Подтверждение:**
- `apps/api/test/health.e2e-spec.ts` — время из подменённого `ClockService`, заголовки helmet, CORS и preflight, request-id, JSON-404 вне префикса.
- `apps/api/test/error-format.e2e-spec.ts` — 404, валидация с `details.fields` (включая вложенное поле), битый JSON, `DomainError` → 422, необработанное исключение → 500 без утечки причины.
- `apps/api/test/swagger.e2e-spec.ts` — UI и OpenAPI JSON со схемами `HealthResponseDto`, `ErrorResponseDto`, enum `ErrorCode`.
- `apps/api/src/common/logging/logger.options.spec.ts` — значения `Authorization`, `Cookie`, `Set-Cookie` не попадают в лог; `src/config/env.spec.ts`; `src/common/filters/http-exception.filter.spec.ts`.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm --filter api test:e2e`, `pnpm format:check`, `pnpm build` — код 0 на Node 24.21. Вручную: запуск без `API_URL` завершается «Invalid environment variables»; Swagger UI открывается в браузере под CSP helmet без ошибок в консоли.

**Для текста:** `apps/api/src/common/filters/http-exception.filter.ts` — функция `toErrorResponse`: единый контракт ошибок и граница «что видит клиент / что остаётся в логе»; `apps/api/src/config/env.ts` — весь файл: fail-fast конфигурация на Zod в 40 строках.

## 2026-10-13 · T-02 Пакет `shared`

**Сделано:**
- Все 15 enum модели данных, `ErrorCode` (HTTP-ошибки) с таблицей HTTP-статусов и `CatchErrorCode` (нарушения правил улова) — как `as const`-объекты с одноимённым типом-объединением.
- Утилиты времени: `warsawDate(date)` — календарный день в `Europe/Warsaw`, `isInClosedPeriod(date, from, to)` — okres ochronny в формате `MM-DD` с переходом через Новый год.
- `effectivePermitStatus(permit, now)` — вычисляемые статусы `SCHEDULED / ACTIVE / EXPIRED` для оплаченного разрешения (ADR-0005).
- Сборка `tsc` в ESM + `.d.ts` (`dist/`), Vitest, 33 unit-теста.

**Решения:**
- Enum — `as const`-объекты, а не `enum` TypeScript: такую же форму генерирует Prisma, значения взаимно присваиваются без приведения типов и на фронтенде остаются обычными строками.
- Варшавские сутки считаются через встроенный `Intl.DateTimeFormat` с `timeZone: 'Europe/Warsaw'`, без `date-fns-tz`: база часовых поясов есть и в Node, и в браузере, а `shared` остаётся без зависимостей (ADR-0003). `docs/03-architecture.md` → «Время» обновлён.
- Даты действия разрешения в `effectivePermitStatus` — строки `YYYY-MM-DD`, а не `Date`: это календарный день, а не момент времени. Сравнение `warsawDate(now)` с ними — сравнение строк, поэтому формат проверяется (`assertDateOnly`, `RangeError`): `@db.Date`, сериализованная как `2026-07-01T00:00:00.000Z`, иначе молча давала бы `SCHEDULED` в первый день действия. `validTo` включительно: разрешение активно до варшавской полуночи после последнего дня.
- Границы периода в `isInClosedPeriod` включительны; неверный формат `MM-DD` даёт `RangeError`, а не тихое «не попадает» — иначе опечатка в правиле отключала бы запрет.
- 29 февраля запретно всегда, когда запретно 28 февраля. Период «do końca lutego» хранится как `…02-28`; при простом сравнении строк `MM-DD` охрана вида в високосный год снималась бы на день. Правило записано в `docs/02-business-rules.md` → «Уточнения».
- Коды нарушений улова отделены от `ErrorCode`: они не становятся HTTP-ошибкой, а приходят в `violations` ответа синхронизации. Тест проверяет, что два набора не пересекаются.
- Приложения видят `@lowisko/shared` через `exports` → `dist`, то есть только после сборки. Поэтому `shared` собирается при `pnpm install` (`prepare`) и перед корневым `pnpm typecheck`, а его скрипт `dev` — `tsc --watch`. Альтернатива (экспорт исходников через custom condition) отвергнута: API на CommonJS и web на Vite пришлось бы настраивать по-разному.
- Версия Vitest вынесена в `catalog:` — она понадобится и в `apps/web` (T-05).

**Проблемы:**
- Тест «enum совпадают с Prisma» написать нельзя, пока нет схемы; критерий перенесён в T-04.
- Проверено опытом (временный импорт в `apps/api` и `apps/web`): с собранным `shared` typecheck проходит, без `dist` — TS2307. Отсюда сборка перед typecheck. Сами зависимости `workspace:*` приложения добавят в T-03 и T-05.

Оба исправлены и закрыты тестами. Ещё два замечания оформлены критериями: Jest в API должен загрузить ESM-only пакет (T-03), CI собирает `shared` до `lint` и `test` (T-06).

## 2026-10-06 · T-01 Монорепозиторий и инструменты

**Сделано:**
- pnpm workspaces с тремя пакетами (`api`, `web`, `@lowisko/shared`) и общим `tsconfig.base.json`; пакеты пока содержат только заглушки входных файлов.
- ESLint flat config с типовым анализом (`typescript-eslint`, `projectService`) и запретом строковых литералов в JSX-разметке `apps/web/src/**/*.tsx`.
- Prettier, Husky и lint-staged: перед коммитом ESLint и Prettier проходят по изменённым файлам.
- Корневые скрипты `dev`, `build`, `lint`, `typecheck`, `test`, `format` (+ `format:check` для CI).

**Решения:**
- Node 24 — действующая LTS; Node 20 вышла из поддержки, а lint-staged 17 требует Node ≥ 22.22. Версию проверяет `devEngines.runtime` с `onFail: error`: поле `engines` само по себе pnpm не останавливает. Версия pnpm закреплена полем `packageManager` (corepack), версия TypeScript — через `catalog:` в `pnpm-workspace.yaml`, одна на все пакеты.
- TypeScript 6.0.3, а не 7.0: `typescript-eslint` 8.71 поддерживает только `<6.1.0`, а без него нет типового линтинга.
- В базовом tsconfig `lib: ["ES2023"]` и `types: []`: в `shared` нет ни DOM, ни Node-глобалов, поэтому требование ADR-0003 «чистый TypeScript» проверяет компилятор, а не ревью. `web` добавляет DOM у себя.
- Запрет строк в JSX собран из двух правил. `i18next/no-literal-string` в режиме `jsx-only` проверяет текст, шаблонные литералы и видимые атрибуты (`title`, `placeholder`, `alt`, `aria-label`, `aria-description`, `label`); технические (`className`, `type`) не трогает. Плагин пропускает любые атрибуты на `<a>`, `<svg>`, `<text>` и `label`/`aria-description` на нативных тегах — это закрывают два селектора `no-restricted-syntax`. Файлы `*.test.tsx` исключены.
- Граница проверки: строки вне JSX (`toast('...')`, переменная с текстом, `.ts`-файлы) линтер не видит, это остаётся на ревью.
- Markdown исключён из Prettier: он выравнивает таблицы пробелами, это около 400 изменённых строк в 22 файлах документации и шумный diff при каждой смене статуса в ROADMAP.
- Корневые `dev`, `build`, `test` запускаются с `--if-present`: тестовые раннеры появляются в T-02, T-03, T-05, а не здесь. Пока флаг стоит, пакет без скрипта `test` молча выпадает из прогона, поэтому снятие флага с `build` и `test` записано критерием в T-06.

**Проблемы:**
- Локально не было ни pnpm, ни подходящего Node; `nvm install` в неинтерактивной оболочке упал из-за пустого `NVM_DIR`.
- `pnpm add` не запустил `prepare`, хук появился только после `pnpm run prepare`. На чистом клоне `pnpm install --frozen-lockfile` ставит хук сам (проверено).
- Ревью нашло дыры в первой версии запрета строк (атрибуты на `<a>`/`<svg>`, шаблонные литералы) и то, что `engines` не мешал работать на Node 20; обе исправлены.
- Ревью выявило то, что проявится в следующих задачах:
  - файлы вне `include: ["src"]` (`vitest.config.ts`, `vite.config.ts`, `prisma.config.ts`, `apps/api/test`, `apps/web/e2e`) дают в ESLint `Parsing error: ... was not found by the project service`, и lint-staged блокирует коммит — пакету нужен tsconfig, включающий эти файлы, или `allowDefaultProject`;
  - для JS-конфигов (`*.cjs`, `*.mjs`) не заданы Node-глобалы, `process` и `module` дадут `no-undef`;
  - TypeScript 6 при `outDir` требует явный `rootDir` (иначе TS5011) — важно для сборки `shared` в T-02;
  - `isolatedModules` вместе с `emitDecoratorMetadata` (NestJS, T-03) даёт TS1272: интерфейсы в конструкторах импортировать через `import type`;
  - не проверено, проходит ли `typecheck` приложений против несобранного `shared` — решить в T-02 при описании `exports`.

**Подтверждение:** автотестов в задаче нет (нет бизнес-логики), проверено командами:

В `apps/api` и `*.test.tsx` правило не срабатывает.
