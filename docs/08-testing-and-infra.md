Принципы:

- NestJS 12 и `@lowisko/shared` — ESM-only, а API собирается в CommonJS. Jest 30 загружает их через `require(esm)`; для этого нужны Node ≥ 24.9 и флаг `--experimental-vm-modules` (он уже в скриптах `test` и `test:e2e` пакета `api`).
- Время инжектируется (`ClockService`, параметр `now`) — тесты не зависят от текущей даты. Unit-тесты API идут в поясе за UTC (`America/New_York`, `globalSetup` — `apps/api/test/unit-time-zone.ts`, T-25): CI работает в UTC, разработчики — в Варшаве, и код, который читает дату в поясе процесса вместо явного, там не падает. Задача по расписанию проверяется настоящим декоратором `@nestjs/schedule` на фейковых таймерах Jest (`permit-expiry-reminder.job.spec.ts`), включая пояс `Europe/Warsaw` и перевод часов.
- Интеграционные тесты поднимают свой PostgreSQL в контейнере и применяют миграции; данные создаются фабриками (`test/factories`), не общим seed. Контейнер один на прогон (`test/db/global-setup.ts`: `prisma migrate deploy`, затем копия в шаблонную БД `lowisko_template`); тест-файл, которому нужна БД, создаёт свою копию шаблона через `createTestDatabase()` — файлы идут параллельно и не видят данных друг друга. Нужен запущенный Docker.
- Тест IDOR: для каждого маршрута `/orgs/:orgId/*` — запрос от админа другой организации → 403 (в тестах модуля). Сквозной `test/idor.e2e-spec.ts` (T-28) читает маршруты из `/api/docs-json` и проверяет все `/orgs/:orgId/*` и `/admin/*`, а также объекты другой организации по id (`07-security.md`).
- OWASP ZAP baseline (T-28): `pnpm --filter web security:zap` (`playwright.zap.config.ts`) поднимает тот же стек, что `pnpm e2e` (`vite preview` — с `--host`, контейнер ходит на `host.docker.internal`), и запускает `zap-baseline.py` (образ `ghcr.io/zaproxy/zaproxy:2.16.1`) по трём целям: web, публичный JSON API и Swagger UI. Пассивное сканирование, без атак. Каждое правило в `apps/web/zap/rules.tsv` — `FAIL`, кроме принятых с причиной (`WARN` — принятый риск, `IGNORE` — информационное); отчёты HTML/JSON/MD — `apps/web/zap/report/` (не в репозитории), в CI — артефакт `zap-baseline-report` ручного workflow `zap.yml` (в GitHub Actions ещё не запускался — проверить первым прогоном). Нужен Docker. Правило, которого нет в `rules.tsv`, ZAP считает WARN: при смене образа список перегенерировать (`-g`) и сверить. На время прогона `vite preview --host` открыт всем интерфейсам машины (демо-данные): локально — только в доверенной сети.
- Все сценарии Playwright идут под CSP продакшн-сборки (`apps/web/security-headers.ts`): фикстура `e2e/fixtures.ts` роняет сценарий при нарушении политики в любом контексте. Нарушения внутри Service Worker (его консоль) она не видит.
- Доступность (NFR-05, T-29): `expectAccessible(page, screen)` из `e2e/fixtures.ts` прогоняет axe-core по правилам WCAG 2.1 A и AA (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`) и роняет сценарий на любом нарушении. Проверяются основные экраны всех сценариев, 28 точек: каталог с картой, карточка водоёма (и с фото), вход, регистрация, покупка, возврат с оплаты, разрешение с QR и аннулированное, форма улова с нарушением и без сети, реестр, проверка QR (недействительный, публичная часть, инспектор), протоколы, внешнее разрешение и его форма, заявка организации, claim, очереди суперадмина, профиль водоёма, тип разрешения, члены и приглашение, проданные разрешения. Первый прогон нарушений не нашёл (что axe их ловит, проверено страницей с картинкой без `alt`, полем без `label` и низким контрастом). axe проверяет то, что видно автоматически, — клавиатурная навигация и чтение экранным диктором остаются ручной проверкой (T-33).
- Покрытие (NFR-09, T-29): бизнес-логика — это чистые функции `packages/shared` (правила ловли и CatchValidator, цены, статусы, время) и сервисы и задачи по расписанию API. Первые покрыты unit-тестами Vitest (`test:coverage`: правила ≥ 90 %, весь пакет — 99 %), вторые — интеграционными тестами против PostgreSQL: unit-тесты сервисов покрывают только чистые части (около 18 % строк), поэтому NFR-09 для API меряется прогоном `test:e2e:coverage` (`test/jest-e2e-coverage.config.mjs`: те же тесты, `collectCoverageFrom` — сервисы, задачи по расписанию, провайдеры оплаты, guards (`src/modules/**/*.{service,job,provider,guard}.ts`) и обработка фото (`src/common/images`), порог 70 % по строкам, ветвям и функциям). CI запускает его вместо `test:e2e`. Результат T-29: сервисы и задачи — 97,4 % строк, 82,9 % ветвей, 98,7 % функций (758 тестов; `photo-optimizer.ts` в этом прогоне показывается непокрытым — v8 не сопоставил его, его покрывают unit-тесты на 100 %); `packages/shared` — 100 % строк, 98,9 % ветвей.
- Lighthouse CI (NFR-02, T-29): `pnpm --filter web perf:lighthouse` (`playwright.perf.config.ts`, тот же стек, что `pnpm e2e`) загружает от админа демо-организации фото «с телефона» (4000 × 3000 JPEG, нарисованный в браузере) на «Jezioro Srebrne» и запускает `lhci autorun` (`perf/lighthouserc.json`) в Chromium Playwright: каталог `/`, карточка с фото, `/login`, по 3 прогона, мобильный профиль Lighthouse по умолчанию (эмуляция Moto G Power, имитация медленного 4G и 4× замедления CPU). Утверждения — по медианному прогону: Performance ниже 0,80 и Accessibility ниже 0,9 — ошибка, Best Practices и SEO ниже 0,9 — предупреждение; Performance ниже 0,85 (цель NFR-02) — предупреждение в выводе и аннотация теста (решение пользователя в T-29: `vite preview` отдаёт HTTP/1.1, Lantern считает по нему очередь запросов; окончательный замер — за Caddy с HTTP/2 в T-30, а 0,80 ловит регрессию). Тайлы OSM заблокированы (`blockedUrlPatterns`): внешний сервер не нагружается и не делает оценку случайной. Отчёты — `apps/web/perf/report/lighthouse/` (не в репозитории). Lighthouse CI 0.15.1 (Lighthouse 12.6): в Lighthouse 12 нет категории PWA — установку PWA проверяют сценарий Б офлайн и ручной тест. Экраны после входа не меряются: им нужен скрипт входа Puppeteer — те же чанки и компоненты, что у карточки и входа.
- k6 (NFR-01, T-29): `pnpm --filter web perf:load` поднимает тот же стек, импортирует 2000 водоёмов (`WATERS_LIST_LIMIT`) через `POST /admin/waters/import` и запускает `tests/load/api.js` в Docker (`grafana/k6:1.8.2`) прямо на API (`:3100`, без прокси `vite preview`). 50 одновременных пользователей 2 минуты (плюс 30 с разгона и 15 с спада): 40 гостей листают каталог (видимая область вокруг Варшавы, вся Польша — самый большой ответ, цены «od», карточка, правила и типы) и 10 рыбаков (демо-аккаунт с годовым разрешением: разрешения, офлайн-пакет, синхронизация отпущенной рыбы, реестр), с паузами 1–3 с. Пороги: p95 < 300 мс по каждой группе и каждому эндпоинту, ошибок < 1 %, проверок > 99 %; суперадмин раз в 10 с открывает весь каталог (`GET /admin/waters`, без пагинации) — порог 1 с, это цифра для отчёта, не NFR-01. Сводка — `apps/web/perf/report/k6-summary.{md,json}`. Рыбаки — один аккаунт: синхронизация берёт блокировку реестра пользователя, поэтому это худший случай для блокировки; за прогон аккаунт записывает несколько сотен уловов, и `GET /me/catches` меряется на реестре, растущем во время теста (тоже худший случай). Водоёмов в каталоге больше `WATERS_LIST_LIMIT` (2000 импортированных и демо-seed): «вся Польша» меряется на обрезанном ответе (`truncated`) — это и есть самый большой ответ каталога.

Запас до 300 мс — на порядок: VPS (T-30) медленнее ноутбука, но не в десять раз. Отдельный лимит запросов для публичного `GET /waters` не нужен (решение T-29).
- Внешние сервисы (P24, Nominatim, SMTP) в тестах заменены фейками; реальный P24 sandbox проверяется вручную по чек-листу.
- E2E (`pnpm e2e`, `apps/web/playwright.config.ts`) поднимает свой стек: API на `:3100` (`pnpm --filter api e2e:server` — сборка `tsc` в `dist-e2e`, чтобы не стереть `dist` идущего `pnpm dev`, PostgreSQL и Mailpit в Testcontainers (Mailpit — на фиксированных портах `:3125` SMTP и `:3126` API из `playwright.config.ts`, не на портах `docker compose`; сценарии читают из него ссылки писем, `emailLink` в `e2e/helpers.ts`), `prisma migrate deploy` и `prisma db seed` с `SEED_DEMO=true`, затем `node dist-e2e/main.js` с `NODE_ENV=test`, без `.env`; логи API при этом выключены — разбор падения по trace и отчёту, в них есть сеть) и продакшн-сборку web через `vite preview` на `:4173` (прокси `/api` → `API_PROXY_TARGET`). Ключи QR, `JWT_ACCESS_SECRET` и `SEED_DEMO_PASSWORD` генерируются на прогон. Нужен только Docker; `pnpm dev` и его база не затрагиваются. Сценарии идут по очереди (`workers: 1`) на одних данных, в профиле Pixel 7 (Chromium), `pl-PL`, `Europe/Warsaw`; данные — аккаунты и водоёмы демо-seed (`apps/api/prisma/demo-data.ts`). Сценарии: `scenario-mvp.spec.ts` (Д → А → Б онлайн → В) и `scenario-b.spec.ts` (Б офлайн, T-21: два контекста-телефона одного рыбака, `context.setOffline(true)`, перезагрузка без сети через Service Worker продакшн-сборки, синхронизация после `setOffline(false)`) и `scenario-g.spec.ts` (Г, T-22: неподключённый демо-водоём → внешнее разрешение с фото → улов лина по общему правилу, сначала нарушение на устройстве → PDF-реестр сезона через событие `download` → отказ удалить разрешение с уловом) и `scenario-d.spec.ts` (Д полностью, T-23: регистрация представителя с подтверждением по письму → заявка организации → активация суперадмином → claim демо-водоёма «Staw Głęboczek» с документом → одобрение → сезон и фото водоёма → тип разрешения → приглашение инспектора, принятие по ссылке из письма после входа → покупка рыбаком (fake) → аннулирование с причиной → рыбак видит «Unieważnione» без QR); общие шаги — `e2e/helpers.ts`. Сценарий не зависит от сезона: вид и правило выбраны без okresu ochronnego; от дня зависят однодневное разрешение и «уловы за сегодня», поэтому прогон, который пересёк бы варшавскую полночь, сначала ждёт её. SIGTERM от Playwright (`gracefulShutdown`) останавливает API и контейнер на любом этапе, иначе контейнер убирает reaper Testcontainers. Отчёт и trace упавшего прогона — `apps/web/playwright-report`, `apps/web/test-results` (в CI — артефакт `playwright-report`).
- Загруженные файлы: каждый файл интеграционных тестов пишет в свой временный `UPLOADS_DIR` (`test/setup-env.ts`); он общий для тестов файла, поэтому тест, который считает файлы, сначала очищает свою папку (`external-permits.e2e-spec.ts`). В `apps/web` jsdom-`File` внутри `FormData` доходит до `fetch` (undici) пустой частью — тест проверяет только наличие и тип части, содержимое multipart проверено в браузере.

## Окружение

| Переменная | Пример / назначение |
| --- | --- |
| `NODE_ENV` | `development` / `test` / `production`; без значения — `production` (JSON-логи, без `pino-pretty`) |
| `API_PORT` | `3000` |
| `DATABASE_URL` | `postgresql://lowisko:lowisko@localhost:5432/lowisko` |
| `WEB_URL`, `API_URL` | `http://localhost:5173`, `http://localhost:3000` — только origin, без пути: `WEB_URL` сравнивается с заголовком `Origin` (CORS) |
| `JWT_ACCESS_SECRET` | случайная строка ≥ 32 байт |
| `QR_SIGNING_PRIVATE_KEY`, `QR_SIGNING_PUBLIC_KEY` | Обязательны. Ed25519 PEM; `pnpm --filter api keys:qr` печатает новую пару двумя строками для `.env` (PEM в одну строку с `\n`). API не стартует, если ключ не Ed25519 или публичный не от этого приватного. Смена пары делает недействительными все показанные QR. В тестах пара генерируется на каждый файл (`test/setup-env.ts`) — ключей в репозитории нет |
| `PAYMENTS_PROVIDER` | `fake` (dev, тесты; по умолчанию) или `p24`. При `NODE_ENV=production` `fake` запрещён — API не стартует |
| `P24_MERCHANT_ID`, `P24_POS_ID`, `P24_API_KEY`, `P24_CRC` | Обязательны при `p24`; панель P24 → «Moje dane» → «Dane API» (`P24_API_KEY` — «klucz do raportów») |
| `P24_BASE_URL` | Origin без пути; по умолчанию sandbox `https://sandbox.przelewy24.pl` — и в рабочей среде дипломного проекта тоже, намеренно (ADR-0004: без реальных денег); боевой P24 — `https://secure.przelewy24.pl` |
| `SMTP_URL`, `MAIL_FROM` | `smtp://localhost:1025` (Mailpit) |
| `NOMINATIM_URL`, `NOMINATIM_USER_AGENT` | По умолчанию `https://nominatim.openstreetmap.org`; публичный Nominatim требует идентифицирующий User-Agent (`lowisko/1.0 (email)`). Без `NOMINATIM_USER_AGENT` API стартует, но строки импорта без координат отклоняются |
| `UPLOADS_DIR` | `./uploads` — каталог `StorageService` относительно рабочего каталога API (`apps/api` при `pnpm dev`); в `.gitignore` |
| `SEED_DEMO`, `SEED_DEMO_PASSWORD` | Только для `prisma db seed`: `SEED_DEMO=true` добавляет демо-данные (`apps/api/prisma/demo-data.ts`), тогда обязателен `SEED_DEMO_PASSWORD` (8–128 символов) — пароль всех демо-аккаунтов, в репозитории его нет. Повторный запуск выставляет его заново |
| `API_PROXY_TARGET` | Web (`vite.config.ts`): куда `vite dev` и `vite preview` проксируют `/api`; по умолчанию `http://localhost:3000`, E2E — `http://localhost:3100` |

`.env` не коммитится; `.env.example` — обязателен и актуален.

## Docker Compose

- `docker-compose.yml` (dev): `db` (postgres:16), `mailpit` (UI на :8025). API и web запускаются локально через `pnpm dev`.
- Refresh-cookie всегда `Secure`: Chrome и Firefox принимают её на `http://localhost`, старые версии Safari — нет; для входа в dev используйте Chrome или Firefox.
- `docker-compose.prod.yml`: `caddy` (HTTPS, проксирует `/api` → api, остальное → статика web), `api`, `db`, том `uploads`.
- NFR-10: `docker compose -f docker-compose.prod.yml up` поднимает всё, включая миграции и seed демо-данных при `SEED_DEMO=true`.

## CI (GitHub Actions)

`ci.yml` на каждый PR и push в `main`:

1. `pnpm install --frozen-lockfile` (кэш хранилища pnpm по `pnpm-lock.yaml`)
2. `pnpm format:check` · `pnpm lint` · `pnpm typecheck` — корневые скрипты сами собирают `packages/shared` и типы API-клиента (`pnpm gen:api`)
3. `pnpm test` (unit), затем `pnpm --filter @lowisko/shared test:coverage` — падает, если покрытие правил ловли и CatchValidator (`packages/shared/src/rules`) ниже 90 % (провайдер `@vitest/coverage-v8`, пороги в `vitest.config.ts`)
4. `pnpm --filter api test:e2e:coverage` (Testcontainers; падает, если покрытие сервисов и задач API ниже 70 %, NFR-09)
5. `pnpm build`
6. Playwright E2E — отдельная задача `e2e` на каждый PR, параллельно с остальными: `playwright install --with-deps chromium`, `pnpm e2e` (Testcontainers на Docker раннера); при падении отчёт и trace — артефакт `playwright-report` на 7 дней

Новый push в ту же ветку отменяет идущую проверку; токен workflow — только чтение.

`performance.yml` — вручную (T-29): Lighthouse CI и k6, отчёты — артефакты `lighthouse-report` и `k6-report` на 30 дней. Не на каждый PR: обе проверки меряют скорость, а общие раннеры GitHub слишком разные для порога на каждом push. В GitHub Actions ещё не запускался — проверить первым прогоном.

`deploy.yml` — по тегу `v*`: сборка образов → GHCR → SSH на VPS → `docker compose pull && up -d`.

## Данные каталога

- CSV в `data/waters/*.csv`, формат:

```csv
source,sourceRef,name,type,region,externalOwnerName,externalInfoUrl,lat,lng,geocodeQuery
RZGW,WA-123,Zalew Zegrzyński,RESERVOIR,mazowieckie,RZGW Warszawa,https://...,,,"Zalew Zegrzyński, mazowieckie"
```

- Пустые `lat/lng` → геокодирование по `geocodeQuery` через Nominatim (`countrycodes=pl`): не чаще 1 запроса в секунду на процесс (`MinIntervalLimiter`; не запускайте CLI-импорт одновременно с импортом через API — получится 2 req/s), результат в `GeocodeCache`; неудачные строки попадают в отчёт импорта, а не роняют его. Полный формат и правила — `data/waters/README.md`.
- Импорт: `POST /admin/waters/import` или `pnpm --filter api import:waters data/waters/<file>.csv` (CLI запускается через `tsx` и собирает сервисы вручную, без Nest DI; путь — относительно каталога вызова; код выхода 2, если есть неудачные строки).
- В тестах геокодер — `FakeGeocoder` (`apps/api/test/geocoding`), его подставляет `createTestApp`; реальных запросов к Nominatim нет.
- Первый регион — Mazowsze: списки łowisk RZGW Warszawa и Okręgu Mazowieckiego PZW (собираются вручную, ссылка на источник — в `externalInfoUrl`).
- Seed (`prisma/seed.ts`): виды (~15) и общие правила; при `SEED_DEMO=true` — 2 демо-организации (`ACTIVE`) с подключёнными водоёмами (`source=MANUAL`, `sourceRef=DEMO-*` — импорт каталога с ними не совпадает) и два неподключённых водоёма: с użytkownikiem rybackim для сценария Г (T-22: «Jezioro Wąsosze») и для claim в сценарии Д (T-23: «Staw Głęboczek»; повторный запуск не трогает их статус, владельца и описание — если водоём забрали claim во время демонстрации, он остаётся у организации с её описанием; `importedAt` демо-водоёмов — момент запуска seed), типы разрешений, правила уровня организации и водоёма, админы, инспектор, суперадмин и рыбаки: с годовым разрешением и уловами за последние дни, без разрешений, младше 16 лет. Пароль — `SEED_DEMO_PASSWORD`, список аккаунтов — `README.md`; повторный запуск отзывает сессии демо-аккаунтов (`07-security.md`). Организации — по фиксированному id: если их NIP уже занят другой организацией, seed останавливается. Даты разрешений и уловов отсчитываются от варшавской даты запуска, вердикт улова даёт `validateCatch` — реестр согласован с правилами в любой сезон. Настройка (организации, водоёмы, аккаунты, типы, правила) перезаписывается при каждом запуске — кроме срока, льготы и водоёмов проданного типа (`02-business-rules.md`); разрешения, уловы и протокол создаются, если их фиксированного id нет (удалённый в окне BR-07 улов вернётся, датированный от дня нового запуска). Правила для проверки демо-уловов отбираются так же, как `SpeciesRulesService.effectiveOnWaters`.
