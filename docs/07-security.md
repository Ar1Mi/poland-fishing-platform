# 07. Безопасность и RODO

## Угрозы и меры

| Угроза | Мера | Где |
| --- | --- | --- |
| Кража токена | Access JWT 15 мин в памяти (не localStorage); refresh 7 дней в cookie `httpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`; ротация, повторное использование отзывает семью. Остаточный риск: выданный access-токен действует до 15 мин после выхода или сброса пароля (не хранится на сервере) | AuthModule |
| Перебор паролей, нагрузка, спам | `@nestjs/throttler`: login 5/мин на IP+email; все публичные auth-маршруты, кроме refresh, — 20/мин на IP (каждый запрос может стоить хеша argon2 64 МиБ или письма); forgot-password — 3/ч на email (нельзя засыпать ящик письмами или бесконечно аннулировать ссылку жертвы); reset-password проверяет токен до хеширования; argon2id | AuthModule |
| Перечисление email | Одинаковый ответ на forgot-password для существующих и несуществующих адресов (токен и письмо создаются без ожидания, чтобы не выдать адрес временем ответа); login для несуществующего email сверяет пароль с фиктивным хешем. Принятый компромисс: регистрация отвечает `EMAIL_TAKEN` — понятность для пользователя важнее; перебор адресов через неё ограничен лимитом 20/мин на IP | AuthModule |
| Захват сессии после смены пароля | Сброс пароля отзывает все refresh-токены пользователя; ротация и отзыв токенов одного пользователя идут последовательно (advisory-lock транзакции), поэтому refresh в момент сброса не оставляет рабочего токена | AuthModule |
| Подделка QR | JWS Ed25519 (`jose`), payload `{ sub: permitId, exp }`; приватный ключ только на сервере (env); проверка подписи **и** текущего статуса в БД | PermitsModule, InspectionsModule |
| Скриншот чужого QR | Инспектор видит имя и год рождения, сверяет с документом | InspectionsModule |
| Утечка данных через публичную проверку | Публично — только действительность, тип, организация, срок, водоёмы и инициалы; имя, год рождения, номер и уловы — только `INSPECTOR`/`ORG_ADMIN` `ACTIVE`-организации-владельца. Ответ `Cache-Control: no-store` (зависит от токена). Поддельный, истёкший токен и неизвестное разрешение неотличимы. Присланный неверный access-токен — 401, а не гостевой ответ. Уловы — только этого разрешения за сегодня, не со всех водоёмов, и без координат. Токен из пути не пишется в лог запросов (T-19) | InspectionsModule |
| Подделка оплаты | Статус `PAID` только по уведомлению P24 с верной подписью **и** успешным `transaction/verify`; сумма сверяется с `Payment.amountGrosze` (иначе 400 `PAYMENT_AMOUNT_MISMATCH`, платёж остаётся `PENDING`); идемпотентность по `sessionId`: уведомление для платежа не в `PENDING` ничего не меняет и не подтверждается. Возврат браузера на `/payment/return` статус не меняет — страница только опрашивает API | PermitsModule (`permits/payments`) |
| Оплата «фейком» в рабочей среде | `POST /payments/fake/:sessionId/complete` отвечает 404, если `PAYMENTS_PROVIDER` не `fake`, а `POST /payments/p24/notification` — если не `p24` (иначе фейковый адаптер принял бы неподписанное тело); при `NODE_ENV=production` API с `fake` не стартует (проверка окружения, T-14) | PermitsModule (`permits/payments`) |
| Поддельное уведомление P24 | `POST /payments/p24/notification` публичный: подлинность доказывают контрольная сумма SHA-384 с ключом CRC (сравнение за постоянное время), наши `merchantId`/`posId`, валюта `PLN` и последующий `transaction/verify`. Иначе 400 `VALIDATION_FAILED`, в лог — только причина, без тела. Фильтр по IP-адресам P24 (рекомендация документации P24) не применяется — принятый риск (T-14): за туннелем или прокси адрес источника недостоверен, а без CRC-ключа подделать сумму нельзя | PermitsModule (`permits/payments`) |
| Открытый редирект со страницы фейковой оплаты | `returnUrl` из адреса страницы выполняется только как путь этого же приложения (`safeReturnPath`; путь с `//` в начале — тоже на главную), иначе — на главную | web |
| «Заморозка» нового типа разрешения | Принятый риск (T-13): брошенная оплата (`CANCELLED`) фиксирует срок, льготу и водоёмы типа и запрещает его удаление, поэтому любой рыбак может так закрепить условия нового типа. Ущерб — администратор создаёт новый тип; лимит покупок на пользователя — кандидат для T-28 | PermitsModule |
| Общий пароль демо-аккаунтов | `SEED_DEMO=true` (T-20) создаёт 7 аккаунтов, в том числе суперадмина, с одним паролем из `SEED_DEMO_PASSWORD`: в репозитории его нет, без него seed не стартует, при `NODE_ENV=production` — не короче 16 символов. Повторный seed отзывает refresh-токены и одноразовые ссылки демо-аккаунтов, как смена пароля, поэтому смена `SEED_DEMO_PASSWORD` обрывает выданные сессии (access-токен — до 15 мин). Вход ограничен throttler, сброс пароля по почте невозможен (домен `.test`). Демо-организации ищутся по фиксированному id, а не по публичному NIP: заявка с NIP из репозитория не будет переименована и активирована seed, он остановится с ошибкой. Остаточный риск: все, кто знает пароль, — суперадмин публичного демо; пароль задаётся только на время защиты, демо не хранит реальных данных | `prisma/seed-demo.ts` |
| Доступ к чужой организации (IDOR) | `OrgScopeGuard` на всех `/orgs/:orgId/*`; сервисы фильтруют по `organizationId`; тест на каждый маршрут | OrganizationsModule |
| Доступ к чужим уловам/разрешениям | Запросы `/me/*` всегда фильтруют по `userId` из токена, не из параметров | все |
| XSS | React-экранирование; запрет `dangerouslySetInnerHTML`; CSP через `helmet` | web, api |
| CSRF | Refresh-cookie `SameSite=Strict`; остальное — Bearer-токен | AuthModule |
| Данные рыбака на устройстве (офлайн, T-21) | IndexedDB хранит разрешения с `qrToken`, внешние разрешения (T-22, без фото), правила, виды и неотправленные уловы последнего пользователя. Токенов там нет (access — в памяти, refresh — httpOnly-cookie). Офлайн-сессия (ADR-0013) открывается без сети только для владельца этих данных и только 7 дней после последнего онлайн-обновления (срок refresh-cookie). Ответы `/me/permits*` и `/me/catches` — `no-store`; Service Worker кэширует только оболочку, каталог и тайлы, а персональное API — никогда. Отказ refresh (401: пароль сменён, семья отозвана, cookie истёк) сразу стирает владельца и его разрешения — украденный телефон в авиарежиме не откроет офлайн-сессию после смены пароля, если хоть раз увидел сеть. Выход стирает данные пользователя с устройства, при неотправленных уловах — после подтверждения; данные, пришедшие для уже закончившейся сессии, не записываются (поколение сессии). Неотправленные уловы привязаны к `userId` и отправляются только с токеном этого пользователя (`/me`), не от имени запомненного. Остаточные риски: тот, у кого в руках разблокированный телефон без выхода, видит разрешения и QR (то же, что напечатанный PDF) и может записать улов от имени рыбака — сервер примет его только с настоящей сессией этого рыбака; без сети выйти нельзя; неотправленные уловы другого пользователя (с координатами, если их добавили) лежат на устройстве до его входа или выхода | `apps/web/src/shared/offline`, `shared/auth/session.ts` |
| Гонка ротации refresh после возвращения сети | Тихий refresh запускается сразу по событию `online`. Перезагрузка страницы, которая оборвёт его ответ, оставит браузеру старый cookie, и следующий refresh будет повторным использованием (ротация T-07): семья отзывается, пользователь становится гостем. Принято: это защитная реакция, данные не теряются — неотправленные уловы ждут входа. Смягчение (короткий допуск предыдущего токена) — на потом | AuthModule, `session.ts` |
| SQL-инъекции | Prisma; `$queryRaw` только с tagged template | все |
| Экспорт уловов организации (T-24) | Минимизация (решения пользователя): только уловы на проданных разрешениях организации, номер разрешения вместо имени, без координат; `Cache-Control: no-store`. CSV injection: ячейка, начинающаяся с `=`, `+`, `-`, `@`, табуляции или CR, получает `'` и кавычки (`apps/api/src/modules/reports/catches-csv.ts`). SQL-отношение разрешений (ADR-0014) имеет свой тип — произвольный `Prisma.Sql` в запрос уловов не передать | ReportsModule |
| Загрузка вредных файлов | Лимит 5 МБ, проверка типа по сигнатуре (`file-type`) и белый список (документ claim и фото внешнего разрешения — PDF/JPEG/PNG/WebP, фото водоёма — только JPEG/PNG/WebP), случайные имена, ключ вне корня хранилища отклоняется, отдача с `Content-Disposition: attachment`, `nosniff` и `Cache-Control: no-store`; документы claim скачивает только суперадмин, фото внешнего разрешения — только его владелец (T-22: все маршруты `/me/external-permits*` по `userId` из токена, чужое → 404, тесты на каждый); срок хранения документов claim — открытый вопрос, перенесён в T-30 (решение пользователя в T-26: это документы организации, а не данные рыбака; удаление файлов отклонённых заявок потребует сделать `proofFileKey` необязательным). Фото водоёма (T-23) — единственный файл, который отдаётся без входа: оно публично на карточке, загружает его только админ организации, к которой водоём подключён; `attachment` + `nosniff` (в `<img>` показывается, открытое напрямую — скачивается, а не исполняется как страница сервиса), `Cache-Control: public` — новое фото меняет адрес | StorageService |
| Чужой вход по приглашению (T-23) | Токен ссылки — 256 бит, в БД только SHA-256; срок 7 дней; одноразовый (условное принятие). Принятие требует входа **в аккаунт с приглашённым адресом** (вход возможен только с подтверждённым email): пересланное или перехваченное письмо не даёт роли другому аккаунту (403 `INVITATION_EMAIL_MISMATCH`). Повторное приглашение и отмена делают старую ссылку недействительной. Страница принимает приглашение только по кнопке — предпросмотр ссылки почтовым сервисом его не использует. Ответ на приглашение уже состоящего — 409 `ALREADY_MEMBER`: админ организации узнаёт, что у адреса есть аккаунт с этой ролью, — он и так видит своих членов. Удаление члена отменяет ожидающие приглашения на его адрес. После принятия токен убирается из адреса страницы; остаточный риск: до принятия ссылка с токеном лежит в истории браузера — до истечения срока | OrganizationsModule |
| Рассылка писем через приглашения | Принятый риск (ревью T-23): админ `ACTIVE`-организации может слать приглашения на любые адреса без предела (`ThrottlerGuard` — только в `AuthModule`), а название организации, заданное заявителем, попадает в тему письма — риск для репутации домена отправителя. Смягчение: организацию активирует суперадмин вручную, каждое приглашение — в AuditLog (`INVITATION_CREATED`, актор). Мера — троттлинг приглашений на админа и организацию — T-28 вместе с остальными лимитами | OrganizationsModule |
| Текст организации в письме платформы (T-25) | Принятый риск (ревью T-25): причина аннулирования — свободный текст админа организации (до 500 символов) — уходит рыбаку в письме с адреса платформы; тот же вектор, что рассылка через приглашения. Ограничения: письмо текстовое (без HTML и ссылок-кнопок), только владельцу аннулированного разрешения этой организации, аннулирование одно на разрешение и записано в `AuditLog`. Письма в лог не попадают: только тема и коды SMTP, без адреса получателя | PermitsModule (`permits/mails`), NotificationsModule |
| Публичное фото водоёма | Отдаётся потоком (не читается в память на запрос), кэшируется только успешный ответ. Принятый риск (ревью T-23): фото до 5 МБ не уменьшается при загрузке — на мобильной карточке оно может стать LCP-элементом (NFR-02), Service Worker хранит до 10 файлов. Сжатие и удаление EXIF при загрузке (новая зависимость) — T-29 | WatersModule |
| Организация без администратора | Последний `ORG_ADMIN` не снимается и не удаляется (409 `LAST_ORG_ADMIN`), в том числе сам себя; одновременные изменения членов организации идут по очереди (блокировка строки организации) — двое админов не удалят друг друга. Удаление аккаунта (T-26) снимает все его членства под той же блокировкой организаций; последний `ORG_ADMIN` `ACTIVE`-организации удалить аккаунт не может (409 `LAST_ORG_ADMIN`) — из двух последних админов, удаляющих аккаунты одновременно, проходит один. `PENDING`- и `BLOCKED`-организация приглашать не может, поэтому её последний админ уходит, и она остаётся без админа (принятое решение пользователя: право на удаление важнее; вернуть админа может только суперадмин вручную) | OrganizationsModule, AccountModule |
| Заполнение тома `uploads/` | Принятый риск (T-22): любой подтверждённый аккаунт может создавать внешние разрешения и загружать к каждому фото до 5 МБ; предела числа разрешений и троттлинга загрузок нет (`ThrottlerGuard` — только в `AuthModule`). Замена фото удаляет прежний файл, так что объём растёт только с числом разрешений. Мера — предел на пользователя и/или троттлинг загрузок — решение T-28 вместе с остальными лимитами загрузок; до тех пор — мониторинг диска на VPS (T-30) | PermitsModule, StorageService |
| Удаление аккаунта украденным токеном (T-26) | `DELETE /me` требует текущий пароль (решение пользователя); попытки — не больше 5 в минуту на аккаунт (`ThrottlerGuard`, счётчик `password` по `userId`), неверный пароль — 401 `INVALID_CREDENTIALS`. Удаление необратимо и само записано в `AuditLog` (`ACCOUNT_DELETED`) | AccountModule |
| Данные после удаления аккаунта (T-26) | Access-токен анонимизированного аккаунта получает 401 сразу, а не через 15 мин: `JwtAuthGuard` проверяет `deletedAt` (одна выборка по первичному ключу на запрос). Иначе очередь уловов устройства, синхронизированная в эти минуты, привязала бы новые уловы с координатами к удалённому аккаунту. Запрос, прошедший guard за миг до коммита удаления, не допишет данные: запись персональных данных проверяет аккаунт в своей транзакции под блокировкой строки `User`, которую удаление берёт первой (`04-data-model.md`). Refresh-токены и одноразовые ссылки удаляются в транзакции удаления, вход и refresh — 401; вход, совпавший с удалением по времени, может оставить строку refresh-токена — бесполезную (refresh проверяет аккаунт → 401), её удалит ночная очистка. Веб после удаления стирает данные пользователя с устройства | AuthModule, AccountModule, Catches, Permits, web |
| Выгрузка данных (RODO, T-26) | `GET /me/export` — только данные владельца токена, `Cache-Control: no-store`. Без хешей пароля и токенов, без QR-токена (подпись не живёт в файле), без `sessionId` и сырого уведомления платежа, без данных третьих лиц: инспектор протокола не назван, записи журнала — без `diff` (в нём адреса приглашённых) | AccountModule |
| Хранение refresh-токенов (T-26) | Ночная задача (`RefreshTokenCleanupJob`, 3:30 по Варшаве) удаляет токены, истёкшие больше 30 дней назад, отозванные тоже (решение пользователя: 30 дней — время разобрать инцидент). Отозванный, но не истёкший токен хранится: по нему ротация замечает повторное использование и отзывает семью. Удалённый токен при предъявлении — `invalid`, а не `reused`: браузер его уже не пришлёт (cookie истекает вместе с токеном), а украденная копия не дала бы ничего и раньше | AuthModule |
| Секреты | Только env; `.env` в `.gitignore`; `.env.example` без значений | — |
| Цепочка поставок | `pnpm install --frozen-lockfile`; скрипты установки только для разрешённых пакетов (`allowBuilds`); свежие релизы задерживает политика минимального возраста pnpm; CI — триггер `pull_request` (не `pull_request_target`), токен `contents: read`, без сохранения в `.git` | `pnpm-workspace.yaml`, `.github/workflows/ci.yml` |

## RODO

- **Минимизация:** номер karty wędkarskiej необязателен; дата рождения нужна только для льгот (BR-08).
- **Основание и согласие:** чекбокс при регистрации со ссылкой на политику конфиденциальности (страница-шаблон).
- **Доступ:** `GET /me/export` — один JSON-файл со всеми данными пользователя (T-26; состав — `05-api.md`); фото внешних разрешений скачиваются отдельно.
- **Удаление:** `DELETE /me` (T-26, подтверждение паролем) — персональные поля `User` заменяются заглушками, `deletedAt` выставлен (`04-data-model.md` → «Ключевые решения»); уловы остаются обезличенными (для статистики организаций) и без координат; разрешения сохраняются с маскированным владельцем; внешние разрешения — без номера и фото (файлы стираются из `uploads/`), уловы на них остаются; членства, ожидающие приглашения, сессии и одноразовые ссылки удаляются; адрес в принятых приглашениях и в записях журнала о приглашениях стирается. Протоколы, которые пользователь вёл как инспектор, остаются за обезличенной строкой — это записи организации; протоколы проверок его разрешений сохраняют место, время и заметки инспектора — тоже записи организации, владелец в них уже обезличен (в отличие от координат уловов, которые вносил сам рыбак). `Organization.contactEmail` удаление аккаунта не трогает: это контакт организации, указанный заявителем, его правка — вместе с профилем организации (на потом). Удаление последнего суперадмина не ограничено: флаг ставится только через seed или БД, вернуть суперадмина — так же.
- **Сроки хранения:** refresh-токены — 30 дней после истечения (ночная очистка, T-26); документы claim — открытый вопрос, T-30.
- **Координаты улова** видит только владелец; организация видит водоём, но не точку.
- **AuditLog** хранит адрес приглашённого в записях `INVITATION_CREATED` / `INVITATION_CANCELLED` (персональные данные): удаление аккаунта с этим адресом заменяет его на `null` (T-26). Адрес приглашённого, у которого аккаунта нет, остаётся — удалить его через `DELETE /me` нельзя.
- **AuditLog** фиксирует действия админов: аннулирование (`PERMIT_REVOKED`, T-23), решения по claim (T-11), создание, изменение и удаление типов разрешений — в том числе цены (T-12), изменение правил, приглашения, их принятие и отмену, смену ролей и удаление членов, правку профиля и фото водоёма (T-23), активацию и блокировку организаций (`ORG_STATUS_CHANGED`), импорт каталога (`WATERS_IMPORTED`), выгрузку уловов организации в CSV (`CATCHES_EXPORTED`), удаление аккаунта (`ACCOUNT_DELETED`, и `MEMBER_REMOVED` в каждой его организации) (T-26). Запись делается в транзакции самого действия: изменение без записи в журнале (и наоборот) невозможно. Действие без своей транзакции (импорт, выгрузка) записывает `AuditInterceptor` после успеха и до ответа: не записалось — 500 и ответа (файла) нет; импорт, уже выполненный к этому моменту, остаётся без записи — принятый риск, в логе ошибка.
