# ADR-0015: Письма о разрешении — отправляет модуль-владелец, напоминание помечается в `Permit`

- **Статус:** Принято
- **Дата:** 2026-11-09
- **Связано:** FR-21, FR-10, ADR-0002, ADR-0012, `02-business-rules.md` («Напоминание об истечении»), `03-architecture.md`, `04-data-model.md` (`Permit.expiryReminderSentAt`)

## Контекст

T-25 добавляет три письма рыбаку о платформенном разрешении: о покупке (после подтверждённой оплаты или сразу для бесплатного типа), об аннулировании организацией и напоминание о скором истечении (в день `validTo − 3`, только разрешениям от 5 дней — решение пользователя). Первые два вызваны изменением в `PermitsModule` (уведомление P24, аннулирование), третье — временем.

Ограничения:

- ADR-0002: модуль читает чужие данные только через экспортированный сервис. В `03-architecture.md` у `NotificationsModule` были «шаблоны и планировщик напоминаний» и нет зависимостей. Но письмо о покупке шлёт `PermitsModule`, а задаче напоминаний нужны его разрешения: если задача живёт в `NotificationsModule`, модули зависят друг от друга по кругу.
- Письмо не должно ломать изменение: ответ на уведомление P24 (P24 повторяет его до ответа 200) и аннулирование уже свершились.
- Напоминание идёт по расписанию: API может не работать в нужный час (деплой) или работать в нескольких экземплярах; сервер почты может лежать или навсегда отвергать один ящик. Нельзя ни слать дубли, ни молча пропускать.
- Один VPS, одна база (T-30), диплом: без брокера сообщений.

## Варианты

Где решается, что и кому писать:

1. **Задача и письма в `NotificationsModule`, данные через сервисы `PermitsModule`.** Соответствует прежней строке документа. Минус: круговая зависимость модулей (`forwardRef` в Nest), а запрос «какие разрешения ждут напоминания» всё равно пишется по таблицам `PermitsModule` — его логика остаётся у владельца.
2. **События.** `PermitsModule` публикует `PermitPaid` / `PermitRevoked`, `NotificationsModule` подписан и запрашивает данные разрешения. Плюс: `PermitsModule` не знает о письмах. Минусы: новая зависимость (`@nestjs/event-emitter`) или своя шина событий; событие в памяти процесса теряется при падении так же, как прямой вызов; для напоминаний событий нет — нужен тот же запрос по таблицам разрешений.
3. **Решает владелец данных** (выбрано): `PermitsModule` (`permits/mails/`) знает, когда и о каком разрешении писать, и вызывает `MailService`; `NotificationsModule` — только шаблоны pl/en/ru и SMTP, без данных и задач.

Как доставить напоминание:

1. **Cron раз в день без состояния:** в 8:00 письма всем с `validTo = сегодня + 3`. Без изменения схемы. Минусы: простой API в 8:00 теряет напоминания дня; два экземпляра шлют дубли; сбой SMTP — потеря.
2. **Таблица исходящих писем (outbox):** строка на письмо (`kind`, `permitId`, `status`, `attempts`), отдельный обработчик шлёт с повторами. Плюс: «хотя бы одно» письмо, общий механизм для всех писем, история отправок. Минусы: новая сущность и больше кода; при падении после отправки, но до отметки, письмо уходит дважды; для дипломного объёма (единицы писем в день на организацию) — тяжело.
3. **Отметка в `Permit` до отправки** (выбрано; отметку и ежечасный запуск 8–20 по Варшаве выбрал пользователь): поле `expiryReminderSentAt` ставит тот же запрос, что выбирает должные разрешения (`UPDATE … WHERE id IN (SELECT … FOR NO KEY UPDATE SKIP LOCKED) RETURNING`). Параллельные запуски берут разные строки, дублей нет. Письмо, не ушедшее «пока» (нет соединения, таймаут, 4xx), отметку теряет и уходит следующим запуском до `validTo`; ящик, навсегда отвергнутый сервером получателя (5xx на `RCPT TO`), отметку сохраняет и больше не пробуется; три сбоя подряд останавливают запуск (сервер почты лежит). Минус: «не больше одного письма» — при остановке процесса между отметкой и отправкой теряются напоминания одного пакета (до 20).

## Решение

Письма о разрешении шлёт `PermitsModule` через `MailService` после коммита изменения; сбой отправки только логируется, повтора у писем о покупке и аннулировании нет. Напоминание доставляется отметкой в `Permit` до отправки: не больше одного письма на разрешение, с повтором временных сбоев.

## Последствия

- Проще: зависимости модулей без круга (`PermitsModule → NotificationsModule`); одна колонка и частичный индекс вместо отдельной сущности; безопасно при нескольких экземплярах API; выбор разрешений сверяется с правилом из `packages/shared` тестом-матрицей.
- Чем жертвуем: письмо о покупке или аннулировании, не ушедшее из-за SMTP, не повторяется (рыбак видит то же в `/me/permits`); напоминания пакета теряются при остановке процесса посреди запуска. Если письма станут важнее (оплата по ссылке, юридические уведомления) — переход на вариант outbox.
- Таймауты SMTP-транспорта (10 с соединение и приветствие, 20 с тишины): письма отправляются внутри запросов, зависший сервер почты не держит их минутами.
- Код: `apps/api/src/modules/permits/mails/` (`PermitMailsService`, `PermitExpiryReminderJob`), `apps/api/src/modules/notifications/` (`permit-templates.ts`, `MailService` → `MailOutcome`, `mail-transport.ts`), `apps/api/src/common/scheduling/scheduling.ts`, миграция `permit_expiry_reminder`.
