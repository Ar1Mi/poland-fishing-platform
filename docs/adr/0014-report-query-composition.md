# ADR-0014: Отчёт по данным двух модулей — композиция SQL-отношения владельца

- **Статус:** Принято
- **Дата:** 2026-11-07
- **Связано:** FR-19, ADR-0002, ADR-0010, `03-architecture.md`, `04-data-model.md` (`Inspection.organizationId`)

## Контекст

Статистика и экспорт уловов организации (T-24) показывают уловы **на её разрешениях** (решение пользователя: минимизация, как у проверки инспектора T-19). Улов хранит только `permitId` (`CatchesModule`), а что разрешение принадлежит организации, знает `PermitsModule` (`Permit → PermitType.organizationId`, только проданные — `PAID`, `REVOKED`).

ADR-0002 запрещает модулю читать чужие таблицы: только через экспортированный сервис владельца. Один и тот же запрос нужен с двух сторон: фильтр — по таблицам разрешений, группировка и строки — по таблице уловов. Объём: за годы у организации тысячи разрешений, за сезон — до десятков тысяч уловов. Требование производительности — NFR-01, отчёт открывают редко, но он не должен тянуть всё в память.

Ранее для похожей задачи (протоколы организации, T-19) выбрали денормализацию `Inspection.organizationId` — «без join в таблицы PermitsModule».

## Варианты

1. **Список id.** `PermitsModule` отдаёт id проданных разрешений организации, `CatchesModule` фильтрует `permitId = ANY($ids)`. Граница чистая и по данным: модули обмениваются значениями, любой из них можно вынести в сервис. Минус: в каждый запрос уходят все id за все годы (тысячи UUID, мегабайты параметров у крупного округа PZW), растут с каждым сезоном; номер разрешения для CSV — ещё один запрос.
2. **Денормализация `CatchRecord.organizationId`** (как `Inspection.organizationId`). Уловы фильтруются по своей колонке с индексом, `CatchesModule` читает только свою таблицу. Минусы: миграция с заполнением существующих уловов, синхронизация пишет поле (его надо брать у `PermitsModule` при каждом улове); у внешних разрешений организации нет — поле `NULL`; статус «продано» всё равно живёт в `Permit` — неоплаченное разрешение без join не отличить; номер разрешения для CSV по-прежнему у `PermitsModule`.
3. **Read model / отдельный модуль отчётов, читающий все таблицы.** Один SQL с join, самый простой код. Минус: прямо нарушает ADR-0002 — `ReportsModule` знает структуру таблиц двух модулей, любое их изменение ломает отчёт молча.
4. **Композиция SQL.** `PermitsModule` отдаёт не данные, а запрос: `ReportPermitsService.ofOrganization(orgId)` — SQL-фрагмент (`Prisma.sql`, параметры привязываются) отношения `("id", "number")` проданных разрешений. `CatchesModule` присоединяет его в своём запросе как подзапрос, не зная таблиц разрешений. Плюсы: один запрос к БД без списков id, SQL каждой таблицы — у модуля-владельца, правило «что значит продано» — в одном месте; схема не меняется. Минусы: граница модуля проходит по коду, а не по данным — оба модуля обязаны жить в одной базе; вынести `PermitsModule` в отдельный сервис для этого запроса без переделки (на вариант 1 или 2) не получится.

## Решение

Вариант 4 (выбор пользователя): владелец данных отдаёт SQL-отношение со своим смыслом, потребитель присоединяет его по ключу. Отношение имеет собственный тип `OrgPermitsRelation` — его создаёт только `ReportPermitsService`, произвольный `Prisma.Sql` в запрос уловов не передать.

## Последствия

- Проще: отчёт по двум модулям — один запрос с индексом `CatchRecord(permitId)`, без миграции и без растущих списков параметров; правило «продано = `PAID` + `REVOKED`» одно для списка проданных (T-23) и для отчёта.
- Сложнее: ADR-0002 уточняется — модуль может отдать **запрос** к своим таблицам как часть своего API, но не таблицы. Обещание ADR-0002 «модуль можно выделить в сервис» для таких запросов выполняется только после замены на вариант 1 или 2 — это цена, записанная здесь, а не скрытая.
- Не для записи: композиция — только для чтения отчётов; изменения по-прежнему идут через методы сервисов и транзакции модуля-владельца.
- Код: `apps/api/src/modules/permits/report-permits/report-permits.service.ts` (`ofOrganization`, `OrgPermitsRelation`), `apps/api/src/modules/catches/report-catches/report-catches.service.ts` (`JOIN (${permits})`), `ReportsModule` только собирает ответ.
- Документация: `03-architecture.md` — правило зависимостей ссылается на этот ADR.
