# ADR-0016: Экспорт и удаление аккаунта (RODO) — `AccountModule` собирает вклад модулей-владельцев

- **Статус:** Предложено
- **Дата:** 2026-11-11
- **Связано:** FR-02, ADR-0002, ADR-0014, ADR-0015, `07-security.md` («RODO»), `03-architecture.md`, `05-api.md` (`GET /me/export`, `DELETE /me`)

## Контекст

T-26 реализует права субъекта данных: `GET /me/export` (JSON со всеми данными пользователя) и `DELETE /me` (анонимизация). Данные пользователя лежат в таблицах разных модулей: профиль и токены — `UsersModule` и `AuthModule`, членства и приглашения — `OrganizationsModule`, разрешения, платежи и внешние разрешения с фото — `PermitsModule`, уловы — `CatchesModule`, протоколы проверок — `InspectionsModule`, журнал — `AuditModule`.

Ограничения:

- ADR-0002: модуль читает и меняет чужие таблицы только через экспортированный сервис модуля-владельца.
- В `03-architecture.md` экспорт и удаление были записаны за `UsersModule` «без зависимостей». Но `UsersModule` импортируют `AuthModule`, `OrganizationsModule`, `PermitsModule`, `CatchesModule`, `InspectionsModule`: если он сам начнёт вызывать их сервисы, модули зависят друг от друга по кругу (Nest разрешает это только через `forwardRef`).
- Удаление должно быть атомарным: аккаунт, у которого сняты членства, но остались координаты уловов (или наоборот), — хуже, чем отказ. Файлы фото не участвуют в транзакции БД.
- Удаление может быть запрещено правилом другого модуля (последний `ORG_ADMIN` `ACTIVE`-организации — решение пользователя), и проверка должна видеть то же состояние, что и само удаление.
- Без брокера сообщений и без новых зависимостей (диплом, один VPS).

## Варианты

1. **`UsersModule` вызывает всех через `forwardRef`** — маршруты остаются там, где записаны в документах. Минусы: круговые зависимости модулей, которые ADR-0002 и ADR-0015 как раз обходят; порядок создания провайдеров становится хрупким; `UsersModule` знает про все таблицы проекта.
2. **События** (`@nestjs/event-emitter`: «пользователь удаляется», каждый модуль подписан) — модули не знают друг о друге. Минусы: новая зависимость; синхронные подписчики в одной транзакции — неявный порядок блокировок, а отказ одного (последний админ) должен откатить остальных — у событий нет естественного «нет»; экспорт событиями не собрать.
3. **Отдельный модуль-оркестратор `AccountModule`** — импортирует модули-владельцы и вызывает их экспортированные методы: `…ForExport(userId)` для экспорта и `…(tx, userId)` для удаления в одной транзакции, которую он открывает. Каждый модуль меняет только свои таблицы. Минусы: ещё один модуль; появляются методы, которые нужны только ему; о новых персональных данных (фото улова, T-27) нужно не забыть сказать ему.

## Решение

Вариант 3. `AccountModule` (`modules/account`) владеет маршрутами `GET /me/export` и `DELETE /me` и не владеет таблицами. `GET /me`, `PATCH /me` остаются в `UsersModule`. Удаление — одна транзакция в фиксированном порядке блокировок; файлы фото внешних разрешений удаляются после коммита сервисом-владельцем (как при замене фото, T-22).

## Последствия

- Зависимости в одну сторону: `AccountModule` → Users, Auth, Organizations, Permits, Catches, Inspections, Audit; его никто не импортирует.
- `AuthModule` впервые экспортирует сервисы (`RefreshTokenService`, `OneTimeTokenService`, `PasswordHasher`) — только для `AccountModule`.
- Новые персональные данные (фото улова и предложения водоёмов — T-27) должны добавить свой вклад в экспорт и удаление: записано в `03-architecture.md` и ROADMAP T-27.
- Документы: `03-architecture.md` (таблица модулей), `05-api.md` (детали маршрутов), `07-security.md` (что анонимизируется), `04-data-model.md` (заглушки в полях `User`).
